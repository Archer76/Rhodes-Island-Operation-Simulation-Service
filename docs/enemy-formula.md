# 敌人正文 → 公式项

把 PRTS 敌人页上的**机制正文**（能力 / 天赋 / 描述 / 敌方技能）编译成可结算的
公式项，口径与干员侧的 `docs/formula-model.md` 一致。

命令：

```powershell
python -m ak_tactic enemydb formula 死志的凝结        # 一个敌人的全部公式项
python -m ak_tactic enemydb formula 源石虫 --json     # 机器可读
python tools/check_enemy_formula.py                   # 自检 118 项
```

---

## 一、为什么不直接复用干员的规则表

`ak_tactic/formula.py` 的 130 条规则是**吃 gamedata 正文**长出来的：游戏内文本
只有 `<$ba.xxx>` 标签与 `{key:spec}` 占位符，`formula.normalize` 直接吃得下。

敌人正文来自 **PRTS 的 wikitext**，多夹着一层 wiki 模板：

| 原文 | 期望 |
|---|---|
| `{{术语\|ba.stun\|晕眩}}` | 晕眩 |
| `{{color\|#FF4F0B\|第一形态}}` | 第一形态 |
| `{{异常效果\|失衡\|免疫}}` | **失衡免疫**（两个位置参数要拼成一个词） |
| `{{修正lite\|并不会失效\|原文=……\|原因=6}}` | 并不会失效 |

不展开就直接匹配，规则咬到的是**模板名**而不是机制名。

### 1.1 `detemplate` 的四个要点

1. **从最内层往外替换**（正则 `\{\{([^{}]*)\}\}` 循环）。不能用
   `wikitext.iter_templates` 逐层剥——它只给**顶层**片段，遇到整段只有嵌套模板
   （`{{color|#FFF|{{术语|ba.stun|晕眩}}}}`）会一条都展不开就退出；
   从最内层往外则天然收敛。
2. `_TPL_ARG` 定每个模板取第几个位置参数：`术语` 取 **1**（第 0 个是内部术语 id
   `ba.stun`）、`color` 取 1、`特殊机制`/`修正lite` 取 0。
3. `异常效果` 属 `_CONCAT_TPL`，位置参数**拼成一个词**——只取第 0 个会丢掉「免疫」。
4. 不认识的模板取**最后一个非空位置参数**（通常是显示文字）。
   宁可留下一个词，也不要让花括号混进正文。

### 1.2 单位引用必须在 `normalize` 之前抢救出来

PRTS 用尖括号表示**单位引用**：`<无谓>`、`<大君之触>`、`<R系列动力装甲>`。
而 `formula.normalize` 的 `TAG_RE` 会把 `<...>` 当富文本标签**整段剥掉**：

```
召唤1个<无谓>   →（不救）→  召唤1个        ← 召唤的是什么，没了
召唤1个<无谓>   →（救）  →  召唤1个「无谓」  ← 语义保住了
```

「召唤出了什么」是这条语料**唯一**的语义，丢了等于没解析。

判据是"像不像真标签"而不是"有没有尖括号"：真标签以 `$` / `@` / `/` 开头
（`<$ba.stun>`、`<@ba.vup>`、`</>`），或是 `br` / `color=…` 这类 HTML。
中文名、带引号的名字、型号名都没有这些前缀。见 `_UNIT_REF`。

## 二、两套规则怎么合

```python
RULES_ENEMY = formula.RULES + ENEMY_RULES     # 干员规则在前
```

**顺序是这个设计里唯一要紧的东西**。`formula.parse` 按表序扫描、命中即
消费文字区间，所以：

- 干员的 130 条在前 —— 它们已经把"数值 + 量纲（PCT / RATIO / FLAT / SCALE）
  + 表达式成形"这套练熟了，「造成攻击力210%的法术伤害」必须归它。
- 敌人规则只补干员**不认识的概念**。

反过来（敌人规则在前）会让粗粒度的敌人规则先咬走带系数的伤害句，
**系数丢了而表达式看起来还是对的**。

### 2.1 敌人新立的 15 个 kind

`block` 阻挡 / `invincible` 无敌 / `immune` 免疫 / `revive` 重生 / `form` 形态 /
`movespeed` 移速 / `reflect` 反射 / `stealth` 隐匿 / `dot` 持续伤害 /
`selfharm` 自伤 / `aura` 光环 / `fly` 移动方式 / `taunt` 嘲讽 /
`channel` 蓄力 / `fragile` 脆弱。

不硬塞进 `buff`/`flag` 的理由：「查出所有无敌的敌人」不该是一次全文搜索。
`_LABEL` 加键是纯增量，干员侧任何已有 kind 不受影响。

### 2.2 给 `_expr` 补了 `form="word"`

敌人的很多机制**没有数值**（无敌、不可阻挡、隐匿），语义全在词里。
原有形状在取不到数值时返回 `"?"`，而 `parse` 只在 `expr` 为空时才用 `flag` 兜底
——`"?"` 非空，`flag` 就永远填不进去。新增的 `word` 形状返回空串。

## 三、三处必须区分的语料特性

### 3.1 中文数字：量词里是**习语**，序数里是**真数值**

干员侧的 `{N}` 接受「一/二/两/三」。用在敌人正文上会出事——PRTS 是人写的散文，
中文数字几乎只出现在习语里：

```
「【最后的奖赏】蓄力一段时间后」  →  蓄力 + 一 + …  →  持续 1s   ✗ 编出来的
```

「一段时间」不是 1 秒。但序数是另一回事：「切换至第**二**形态」的「二」是真数值。
所以分开两个占位符：`_DNUM`（只要阿拉伯数字）用于量词，`_DORD`（含中文数字）
用于序数。

### 3.2 `攻击速度+50` 与 `攻击速度提升50` 不是同一句话

干员的 `buff_atk` / `buff_aspd` 只认**游戏内的 `+N` 记法**——因为 gamedata 的
正文本来就是那样写的。PRTS 的敌人正文是手写的，用「攻击力提升50」这种自然语句，
直接漏掉一大片。故补 `e_attr_up` / `e_attr_down`，以及无数值的
`e_attr_word_up` / `e_attr_word_down`（「·攻击速度提升，」——真数据在黑板里，
正文只说了方向）。

### 3.3 覆盖率不是正确率

第一版把「释放」「放下」也算作召唤，`e_summon` 命中 **1007** 次排第一。
逐条看证据才发现绝大多数是「释放源石技艺」「释放当前波次」「放下结晶」
——**不是召唤**。剔掉后降到 756 次，总覆盖率从 59.0% 掉到 58.1%。

那 0.9 个百分点掉得对。**这条记在 `[5] 精度守卫` 里**，一共 12 条守卫，
每条都对应一次真实的过度匹配。

## 四、运算符与落点

`op` 沿用干员侧的词汇，但基准是**文本主语（即这个敌人自己）**：

| op | 敌人侧的含义 |
|---|---|
| `self` | 这个敌人自身（绝大多数增益、形态、无敌） |
| `ally` | 敌方阵营（召唤物、光环回复） |
| `enemy` | **我方**（干员与召唤物）——敌人造成的伤害落在这里 |

不变的量纲机器：`PCT`（文面 210% 已是百分数，**再乘 100 就是 21000%**）、
`RATIO`（黑板 `{atk:0%}` 存的是 0.14）、`FLAT`、`SCALE`。干员侧那条量纲
不变量在敌人语料上照常成立（`check_enemy_formula` 第 [4] 节有守卫）。

| 来源 | 条数 | 仅干员规则 | 加敌人规则（第一轮） | 第二轮 | 加算式 |

| skill | 1,352 | 28.6% | 65.6% | 73.4% | **75.2%** |
| ability | 1,574 | 8.8% | 58.4% | 70.7% | **70.8%** |
| ability_fixed | 114 | 14.0% | 64.0% | 73.7% | 73.7% |
| desc | 2,025 | 6.8% | 36.5% | 44.4% | **44.7%** |
| **合计** | **6,935** | **20.2%** | **60.2%** | **68.2%** | **69.3%** |

规则：干员 130 条 + 敌人 68 条 = 198 条，另有一个**算式 pass**（见 5.7）。

### 5.1 `desc` 覆盖率低是**对的**

2,025 条描述里大量是剧情与风味文本：「只是很简单的愿望。和想要活着一样简单，
也一样难以摆脱。」这类**本来就不该被解析**。自检里因此有一条**上限**守卫
（`desc ≤ 55%`）——解析率过高反而说明规则过宽。

### 5.2 剩余缺口是**长尾**，不是「差几条规则」

第二轮补规则前先把缺口量了一遍，结论决定了这一轮的做法：

- 未覆盖的**去重**条目 873 条（非 desc，共 41,037 字）
- 按 `·`/`※`/`。`/`；`/`、`/`，` 切开后是 **1,876 个互不相同的短句**
- 最高频的短句只出现 **20 次**，多数是 2–4 次

也就是说剩下的主体是**一次性文案**，不是反复出现的机制。所以第二轮只补
**成簇的家族**（同一机制反复出现、措辞收敛的那几类），不去逐条凑长尾——
逐条凑等于手工录入，覆盖率的分子会涨，正确率不会涨。

### 5.3 第二轮补的 15 条家族规则

| 家族 | 代表句式 | 新规则 |
|---|---|---|
| 阻挡门槛 | 只能被阻挡数大于等于3的单位阻挡 / 占用3个阻挡数 | `e_block_threshold` `e_block_occupy` |
| 否定式属性 | 无法被攻击 / 不可沉默 / 不可对空 | `e_unattackable` `e_silence_immune` `e_no_air` |
| 索敌 | 索敌不受阻挡影响 / 优先攻击指挥终端 | `e_target_ignore_block` `e_target_priority` |
| 元素损伤 | 每次攻击造成一定侵蚀损伤 | `e_ep_damage` `e_ep_damage_attack` |
| 生命流失 / 加速 | 会逐渐损失生命 / 移动时逐渐加速 | `e_lose_hp` `e_speed_accel` |
| 溅射与范围 | 攻击造成法术溅射伤害 / 对周围我方单位造成物理伤害 | `e_splash_damage` `e_around_damage` |
| 生死语义 | 消失时不会扣除目标生命 / 不计入歼灭数 | `e_no_life_cost` `e_death_life_cost` |

**元素损伤**这一类尤其值得单独说：PRTS 手写的敌人正文**不写数值**
（「造成一定侵蚀损伤」），真值在敌人同档黑板上。所以 `e_ep_damage` 只认种类、
量纲记 `word`、`amount` 留 None——**不编造数值**。这与干员侧那些带数值的
`ep_damage` 规则分工不同，两边不能互相顶替。

### 5.4 本轮真踩到的一个静默算错：「提升**至**」

原 `e_movespeed_up` 把「移动速度最终提升至500%」读成 `+500%`。但「提升**至**」
是**设为目标值**（`base × 500%`），而 `+500%` 按 `base × (1 + 500%)` 结算是 6 倍
——**差 6 倍，而且表达式看起来完全合理**。已拆成两条，`e_movespeed_to` 在前：

| 写法 | 命中规则 | 语义 |
|---|---|---|
| 移动速度提升至500% | `e_movespeed_to` | 设为目标值 500% |
| 移动速度最终提升50% | `e_movespeed_up` | 增量 +50% |
| 移动速度降低50% | 干员侧 `debuff_ms_down` | −50% |
| 移动速度变为2倍 | `e_movespeed_times` | 乘 2 |

### 5.5 删掉的「分条目切分」——它是个恒等变换

第一轮的假设是：敌人正文常写成「`·` 开头的一串机制」，这是一张**清单**而不是
一个句子，整句匹配不到，切开就能救。**这个假设是错的。**

规则表全是**无锚定的子串正则**（`re.search`，不是 `fullmatch`）。若整句里任何
位置都没命中任何规则，那么整句的任意子串（=任一条目）里也不可能命中——
**切分对召回率是恒等变换**，可以证，不需要试。

实测也坐实了：语料里整句为空的 2,208 条中，612 条可切分，逐条救回 **0** 条。
反向再验一次「有条目就直接逐条解析」（不先试整句）：覆盖**一样**，却改动了
7 条原本已覆盖文本的旧项——零收益、纯风险。

所以 `split_clauses()` 与它的 `parse()` 包装已删除。涨覆盖的是**新规则**
（60.2% → 68.2%），不是切分。删掉而不是留着，理由是**死代码比不留更坏**：
它会让人以为覆盖是它挣来的。自检里留了一条守卫——若将来有人加入**锚定**规则
（`^…$`），那条守卫会变红，提示需要把切分器拿回来。

### 5.6 变化是**纯追加**的

补规则前后逐条对拍（同一份语料、同一份黑板）：

- 0 → 有：**534 条**
- 有 → 0：**0 条**
- 有 → 有但签名变了：**894 条，全部是「旧项 ⊆ 新项」的纯追加**
- 动了旧项：**0 条**

这是能给出的最强精度保证：加规则只让结果**变多**，没有让任何一条已覆盖文本
的解析结果**改变或丢失**。

### 5.7 带变量的算式：**识别与规范化，不求值**

正文里有一类不能按常数提取的东西：

> 静态刚体，每0.1s受到25无来源真实伤害，自身移动速度**+(50%×加速层数)**
> （增益数值仅于特定时机更新），每0.5s检测一次：，①若未受晕眩/束缚影响且
> 自身未被阻挡，获得1层加速层数（最高25层），否则使加速层数归零

`移动速度+(50%×加速层数)` 是**带变量的算式**。这一类不是"漏了"，而是**会算错**：
常数提取会把 50% 当成系数，得到 `ATK × 50%`——**表达式看起来完全合理**，
实际意思是「**每层** 50%」。这正是本项目记录在案的那类真错误。

本轮的做法是**只识别与规范化，不求值**：层数、数量、当前SP 这些变量的值
在运行时才知道，编译期编不出来。产出三项：

| 字段 | 内容 |
|---|---|
| `expr` | 算式的值部分（`(50%×加速层数)`） |
| `formula` | 完整算式写法（`自身移动速度+(50%×加速层数)`） |
| `vars` | 依赖的变量（`["加速层数"]`） |

`amount` **一律为空**——自检里有一条守卫，任何"顺手求个值"的实现都会红。

#### 语料长什么样

含乘号的去重语料 122 条，其中真算式 84 条。形态收敛得很好：

```
(50%×加速层数)              (30×充能层数)%           (100%+增益层数×25%)
(4%+0.5%×倍率层数)           (场上的啸叫音响数量×25%)   (10×汲取体数量)
已处理目标数量/待处理目标总数量×100%    当前移动速度×800        阻挡数×0
(当前SP × 10)%              (载客数×50%)            (20%×场上同构碎片的数量)
```

语法四层就够：`expr := mul (('+'|'-') mul)*`、`mul := value (('×'|'*'|'/'|'÷') value)*`、
`value := 数值['%'] | 变量 | '(' expr ')' ['%']`。

#### 四个必须踩出来的坑

**① `m.lastgroup` 不能用来判 token 类型。** 它返回的是最后一个匹配的**子组**。
`50%` 的 token 同时匹配 `num` 与它的子组 `pct`，`lastgroup` 是 `pct` 而不是 `num`
——于是**所有含百分号的算式都被判成非法**，症状是「`(50%×加速层数)` → None」
而「`(30×充能层数)` 正常」。改用固定优先级逐个查组是否非 None。

**② 变量名里不该有数字。** 中文没有空格，分词只能按标点切，于是散文碎片会被
当成变量：`附着范围为1×1`、`1层攻击力+10%`、`拥有0/20`、`持有不低于1/15`。
一句「变量名不含数字」全部挡掉——真正的变量名里没有数字
（`当前SP` 是字母，`加速层数`、`载客数` 都不是数字）。

**③ 中文里的斜杠常是并列分隔符，不是除号。** `物理/法术伤害-90%` 说的是
「物理和法术伤害都降 90%」。判据是**「左看词尾、右看词头」**：左边常带一长串
定语（`来自正面的物理`），只看词头会漏。两侧都是伤害类型词时一律不当除法。

**④ 同一句里可能有多个算式，收完要接着扫。** `每秒受到(10×汲取体数量)的伤害
与(25×汲取体数量)的损伤`——第一版收完一个就退出整段，后面那个静默丢失。

#### 算式认到哪个属性上

办法是读**最外层运算符的左操作数**（解析器记作 `Expr.lead`）：
`自身移动速度+(50%×加速层数)` 的 lead 是 `自身移动速度`。三条判据：

- `+` / `-` 的 lead 基本就是属性名（`+` 增益、`-` 增益取反）
- `×` 只在**右边没有变量**时才算属性：`阻挡数×0` = 阻挡数归零；
  而 `移动速度×加速层数` 是拿两个量算一个值，不是改属性
- **`当前X` 一律不算属性**：`当前移动速度×800` 是「以移速为**当前值**为系数
  算伤害」。剥掉 `当前` 会把这条误记成「改移速」，表达式还看着对

算式被「提升至」和属性隔开时（`移动速度最终提升至(100%+增益层数×25%)`），
再往宽处找属性名。**认不出就留白**：`attr` 空、kind 记 `formula`，
算式与变量照旧保留，读的人自己看 `context`。

还有一条容易漏的：`_split_lead` 把 lead 从变量里摘出来，**只有当 lead 真的
被当作属性时**才能摘。认不出属性时 lead 就是算式依赖的那个量
（`当前移动速度×800`），摘掉就等于把这条算式唯一的变量扔了。

价值不是"多覆盖几条"，而是把那些行里**原本会算错的常数**换成了保留结构的算式。

### 5.8 已知的两处读不准（宁可留白也不猜）

- `防御力/法术抗性最终×0`——中文的 `/` 又是并列（「防御力和法术抗性都归零」），
  但两侧不是伤害类型词，现有的斜杠判据拦不住。它产出的是 `算式
  法术抗性最终×0 ⟨变量：法术抗性最终⟩`：**字符串是忠实的，语义是并列不是除法**。
  4 处。
- 规则已经咬走的片段，算式不再重复出一项。所以
  `攻击力/防御力降低至已处理目标数量/待处理目标总数量×100%` 只留下
  `e_attr_word_down 减益 降低（幅度未写明） (防御力)`——那句「幅度未写明」其实
  正文是写了的。这是"规则优先"的代价，换来的是**不可能重复计数**。

### 5.9 有意不收的子玩法

按博士裁定，**足球模式、生息演算等子玩法一律不收**。已识别但不再处理：
`场上球员类敌人总数`（足球）、`移动速度×800` 以外的球类机制、
`近地悬浮`/`静态刚体`/`弹性1.0`/`总是瞄准未被遮挡的球门`/`技能期间选取此足球`
（约 100 条，只出现在卫戍协议）。

口令是**「忽视」而不是「过滤」**：这些文本仍照常解析（parser 不区分玩法），
只是不为它们专门写规则、不做专项覆盖统计。

### 5.10 属性表的收录口径（2026-09-16 博士裁定）

裁定原话：「**只留战斗结算有用部分**」。这不是"词表越全越好"——表越宽，
把散文里的名词误认成属性名的机会越多。判据是**模拟器会不会因为这个量而改变结算**：

* **进表**（31 项）：阻挡 / 移速 / 攻防 / 攻速 / 攻击间隔 / 攻击距离 / 重量 /
  生命 / 再部署 / 费用 / SP / 技能优先级 / 嘲讽等级 / 田地病害值 / 飞行速度。
* **不进表**：范围、视野、半径、角度、计数、阈值、占比——要么是派生量，
  要么根本没进结算，收进来只是噪声。

未填的部分按我给的**建议**走，而 93 条建议几乎全是**排除**（散文碎片、
范围记法、发射角度）。守这条口径的不是"逐词拉黑名单"（那会随语料腐烂），
而是 `check_attr_table()` 钉住的**词条形状**：属性名必须是短词、无动词、
不重复。反面例子：`范围内的田地地块病害值`、`每次普通攻击使自身攻击间隔`、
`被该效果击倒的干员再部署时间`。

长度上限最终取 **12** 而不是 8：`可抵抗状态生效时间倍率` 有 11 字，但它是
**真属性名**（敌人正文写「【明力】可抵抗状态生效时间倍率」）。这条阈值是
我先定 10、被它顶红之后才改的——**阈值要按真实反例校正，不能凭手感**。

### 5.11 斜杠是**并列**，这条在这套语料里反复出现

中文里的 `/` 极少是除法。已经碰到四种形态，判据各不相同：

| 写法 | 读法 | 判据 |
|---|---|---|
| `物理/法术伤害-80%` | 两者**都**降 80% | 左看词尾、右看词头都是伤害类型词 |
| `防御力/法术抗性最终×0` | 两者**都**乘 0 | 两侧**都以属性名开头** |
| `攻击力/防御力降低至…` | 两者一起被改 | `_EXPR_SET_TO` 回看段里**每个**属性名都收 |
| `已处理目标数量/待处理目标总数量×100%` | **真除法** | 两侧都不是属性名 |

**取属性名时有两种取法，别混**：`物理/法术伤害-80%` 这类由**规则**匹配，
`attr` 直接写正则组；而算式里的并列由 `_expr_kind` 收集——**按出现位置排序后
用 `/` 连起来**（`攻击力/防御力`）。早期按表序取第一个命中的，于是
`攻击力/防御力` 只记成 `攻击力`，**另一侧的幅度就丢了，而且看起来还挺合理**。

### 5.12 算式与规则抢同一段文字时：**切掉被咬走的那段再试**

原先的约定是「规则已咬走的区间，算式不再出项」（保证不重复计数）。
代价在 `攻击力/防御力降低至已处理目标数量/待处理目标总数量×100%` 上暴露：
规则只收走 `防御力降低` 并留下「降低（幅度未写明）」，而算式从 `攻击力`
起算、整条与它重叠 → 直接跳过，**幅度就丢在正文里了**。

博士裁定「不保留自然语言，写成算式」，对应的正是这一类。改法是**切掉
那一刀重新找**：把 `used` 里与它重叠的部分切掉，在切后的文字上再找第一个
算式。结果 `expr` 拿到分母侧、`formula` 保留完整算式（含分子），幅度不丢。
只切一次、只取切后第一个结果——**这是补漏，不是扩张**。
