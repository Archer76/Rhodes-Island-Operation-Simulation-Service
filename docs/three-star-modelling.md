## 二 · 两条已有证据的结论

### 2.1 天赋的面板倍率**在权威实现里也不算**（所以这不是 Go 的账）

现算（`akdb` 只读 ＋ Go 的 `opstats` ＋ Python 的 `OperatorCalculator`）：

| 干员 | 原始面板（akdb） | 信赖 ＋ 潜能 | Go `total.atk` | Python `stats().total.atk` | 若乘天赋（×1.04）应是 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 玫兰莎 E1L55／信100／潜6 | 738 | ＋65 ＋25 | **828** | **828** | 861.1 |

⇒ **两台引擎一致地没乘**。所以：

* 它**不是**「Go 与 Python 不一致」，而是**共有的口径**：「天赋加成未应用」；
* 但按「完整建模」的要求，它**仍然是一条缺失**——`828` 与真值 `861.1` 差 4%；
* ★ 补它**必然与冻结的 Python 分道扬镳**（`ak_tactic/**` 不许改）⇒ 所有「与 Python 逐字段一致」
  的判据都要跟着改口径，这是**一个独立的决定**，不是顺手能做的。

### 2.2 技能那一支整支没接（Go 自造规格这条路上）

* `rios-sim/operators.go:100` 的 `OperatorUnported = ["skill", "active"]` ⇒ Go 压根不产出这两个键；
* `rios-sim/skill.go:83` `if sk == nil { continue }` ⇒ 技能状态机一步一步都不走；
* 实测：计划里 `skill` 写 **0 或 1，`operators[0].skill` 都是 `null`**，而闸门**两种都不报**
  ⇒ **完全静默**（判决里也看不出来）。
* 登记表那条理由（「24 份夹具 64 人次 `skill` 全是 0 ⇒ 零行使」）**在博士口径下不成立**：
  `skill: 0` ＝ 默认技能＝技 1 ⇒ 是 **64 / 64 人次都在用**。

## 五 · 技能那一支的**模块化设计**（博士要求：高星要能套用）

### 5.1 先量了「键词表」，因为它决定模块的边界

现算（`akdb` 的 `skill_level` 全库 1624 个技能）：

| | 读数 |
| --- | ---: |
| 全库不同黑板键 | **964** |
| **三星那 17 个技能用到的键** | **10** |
| 其中**同时在全库前 40 高频键**里的 | **10 / 10**（一个不落） |

三星用的那 10 个键：`atk`／`def`／`attack_speed`／`base_attack_time`／`cost`／
`heal_scale`／`atk_scale`／`times`／`ability_range_forward_extend`／`attack@range_scale`。

⇒ **模块化是对的路**：这 10 个键在全库的频次分别是 **399／126／119／117／90／40／288／19／21／
（`attack@range_scale` 属长尾）**——即「三星要用的键」恰好是「全库最常用的那几个」，
把「**键 → 修正**」做成一张表，三星是这张表的第一个用户，高星技能自然复用。

### 5.2 模块形态（写进代码时按这个来）

```
键驱动的效果模型（新文件 rios-sim/skilleffects.go）
  · 输入：一次部署的黑板（`skill_level.blackboard`，已由 skillmeta.go 取好）＋ 基准面板
  · 输出：① 一份「修正后的 Profile」② 一份**未识别键清单**（具名，不许静默丢）
  · 表里每一条都是：键名 → 这一条对哪个量做什么（乘／加／换）
      atk                      → 攻击力 ×(1+v)
      def                      → 防御力 ×(1+v)
      max_hp                   → 生命上限 ×(1+v)（走 Profile.MaxHP 那条既有通道）
      attack_speed             → 攻速 +v
      base_attack_time         → 攻击间隔改动
      cost                     → 开技立即 +v 费
      heal_scale               → 自疗量（按上限的 v）
      atk_scale                → 单次攻击倍率
      times                    → 连击次数
      ability_range_forward_extend → 射程前移 v 格
      attack@range_scale       → 溅射半径 ×v
  · **认不出来的键一律进「未识别」清单**并计数——覆盖账要能回答
    「这名干员这个技能，有几个键被认了、哪几个没被认」，而不是「看着像跑了」。
```

★ 验收标准（博士给的那条）：**加一名新干员不需要改判定逻辑**——
只要它的键落在表里就行；落在表外的新键**必须具名出现在覆盖账上**。

★ 这张表**同时服务天赋**：三星的天赋黑板也是同一套键（`atk`／`def`／`max_hp`／
`attack_speed`／`cost`／`atk_scale`＋`prob`），所以「天赋面板倍率族」用它同一份实现，
**不是第二套代码**。

## 六 · 天赋面板倍率族：**影响面先量出来**（决定这一步怎么做）

在做第 ③ 层之前先量影响面（`akdb` 现算，2649 条天赋行）：

| 问 | 读数 |
| --- | ---: |
| 全库有「面板键」天赋的 `char_` 干员 | **212 / 460 ＝ 46%** |
| 按键分 | `atk`×383 ／ `def`×157 ／ `attack_speed`×157 ／ `max_hp`×78 ／ `magic_resistance`×41 ／ `cost`×34 ／ `block_cnt`×23 ／ `base_attack_time`×11 |
| 三星 17 位里有这类天赋的 | **12 位**（键：`atk`×6 位 ／ `max_hp`×2 ／ `def`×1 ／ `attack_speed`×2 ／ `cost`×2） |

⇒ 三条判断：

1. **这一步必然与冻结的 Python 大面积分道扬镳**（46% 的干员面板会动），
   而 Python 侧**一个都不折**。所以它不是「顺手补一条」，而是一次**口径变更**：
   * 受影响的判据要**具名登记**（哪几套、为什么红是对的、改成什么口径）；
   * 冻的基线要**重录**；
   * 而且必须**同一笔里做齐**——只改一半会让「面板」这个量在两个口径之间摆动。
2. **做法仍走同一张键表**（`skilleffects.applyMods`）：天赋黑板与技能黑板共用
   `atk`／`def`／`max_hp`／`attack_speed`／`cost` 这批键，所以这是**复用**，不是第二套代码
   （博士要的模块化：加一名干员不改判定逻辑）。
3. **三星这一批是自然的试点**：12 位、5 个键、值都是简单百分比（`0.03`–`0.12`），
   先把这 12 位点亮并出运行期见证，再决定要不要一次推到全库 212 位。

## 七 · 伤害类型的口径（博士 2026-09-24 给定）与它的落地

> **所有干员只要没有在特性中说明是法术伤害，就都造成物理伤害；如果有另行说明
> （如月见夜的技能、赤刃明霄陈的弱点伤害），那么就在满足条件时切换伤害类型。**

三条落点，逐条落到代码里：

| 口径 | 落地 | 证据 |
| --- | --- | --- |
| ① **基准**：特性没写「法术伤害」就一律物理 | 就用 `OperatorStats.TextDerived.DamageType`（由**特性正文**推出） | 全库特性正文含「法术伤害」的干员 **129 位**，其余一律物理 |
| ② **技能另行说明**：正文写明「伤害类型变为 …」时，**技能开启期间**切换 | `skilleffects.go::DamageTypeFromSkillText(desc, base)` —— **按短语**，不按技能名 | 全库正文含「伤害类型」的技能 **18 个**：`变为法术`／`转变为法术`／`变为物理`／`转化为弱点伤害` … |
| ③ **条件触发的转化**（赤刃明霄陈的弱点伤害） | 同一张短语表里的 `转化为弱点伤害 → WEAKNESS` | `sktok_acarm067_1/2` |

★ 为什么**按短语**而不是按技能 id：这 18 个技能分布在多名干员上，按 id 硬编码就是
「加一名干员改一次判定逻辑」，与博士要的模块化正好相反；短语表可以随新干员自然扩展。
★ 逐条是**整串短语**匹配、不做子串猜测，所以「变为物理」（`skchr_cerber_3` 把法术干员
改成物理）与「变为法术」不会互相误中。

## 十 · 天赋的**非面板**效果（键驱动，2026-09-25）＋ 特性那一族新收的一支

上一个节点（§六）管的是「折进面板的那三个键」——产物是**面板上的一个数**。
这一节管的是**发生在场上、某一时刻才兑现**的那几条：部署那一刻给技力、出手那一刻判概率、
治疗那一刻授闪避。模块是 `rios-sim/talenteffects.go`，**与 `talentpanel.go` 共用同一张键表
与同一个解析器**（`skilleffects.go::ApplyBlackboard`），不是第二套代码。

### 10.1 判据一律是「键的组合」，不是天赋名、不是干员名

博士 2026-09-24 的模块化口径：**加一名新干员（不管几星）不许改判定逻辑。**
三星这一族正好给出四条**互不歧义**的键组合（黑板原文全部现取自 `akdb`）：

| 键的组合 | 效果 | 谁（三星） | 黑板原文 |
| --- | --- | --- | --- |
| `sp` | 部署后立即获得 v 点技力 | 炎熔 快速技能使用 | `{"sp": 15.0}`（E1L55 是 30） |
| `prob` ＋ `atk_scale`（**无** `duration`） | 概率强化当次攻击 → **期望倍率** `1+p(s−1)` | 克洛丝／月见夜 要害瞄准·初级 | `{"atk_scale": 1.5, "prob": 0.1}` |
| `attack@prob`（**无** `atk_scale`） | 附加治疗一名的概率 | 安赛尔 附加治疗 | `{"attack@prob": 0.07}` |
| `prob` ＋ `duration` | 治疗友方后授出持续 v 秒的闪避（值＝`prob`） | 斑点 烟雾加装 | `{"duration": 3.0, "prob": 0.1}` |

### 10.2 `prob` 与 `attack@prob` 是**两个键、两种意思**——`ApplyBlackboard` 把它们归进同一个 `m.Prob`，所以这里**必须回看原始键名**

这不是洁癖，是实测：安赛尔的黑板是 `attack@prob: 0.07`（**没有** `duration`），
斑点的 `prob: 0.1`（**有** `duration`，且没有 `attack@prob`）。
技能侧需要 `m.Prob` 是一个数，天赋侧需要**分开**——「同一个键名被合并成同义词」
正是本仓记过的假信号来源，所以模块里留了一行显式的 `_, hasProb := bb["prob"]`。

### 10.3 概率走**期望值**，不掷骰子

与既有的闪避同一条口径（`resolveDamage` 把 `dodge` 当期望值削掉，`sim.go:3237`）。
掷骰子会让同一条时间线两次跑出两个数，而判决比对靠的就是可重复。

### 10.4 特性那一族新收的一支：「技能可以治疗友方单位」（守护者）

## 十一 · ② 特性·目标选择那两条（2026-09-25 第二批）

### 11.1 ★ 一个真被咬到的坑：**排版标签插在词中间**

泡普卡 `trait_text` 的原文（逐字，取自 `akdb`）是

```
同时攻击阻挡的<@ba.kw>所有敌人</>
```

⇒ 整串短语「同时攻击阻挡的所有敌人」一个字都不差地去扫，**扫不到**。
后果不是报错，而是**那条特性整条静默不生效**——判决上表现为「她一次只打一个」，
与「这条特性没接」一模一样。

本仓为这件事**早就留过注释**（`skillmeta.go:94-98`，出处 `skill.py:134`：
「伤害类型变为<@ba.vup>真实</>」原样扫「真实伤害」是扫不到的），
只是此前没人在**特性**侧撞上。处置是新增 `stripTraitTags`，
并把 `textDerived` 的四条判词**一起**改成扫剥过标签的正文——
只给新加的两条剥、把老的两条（`heals` / `damage_type`）留在原文上，
等于把同一个 bug 留一半。

★ 剥标签是**严格放宽**（只会让命中变多），所以它是一次行为变更，必须量：
`check_operator_go.py` 在 2003 次折算（深扫 468 ＋ 名册 211 ＋ 合成 1324）上
**不一致 0 次** ⇒ 现有这批干员里没有一条因此翻转。

### 11.2 两条的落点与口径

| 机制 | 判据 | 落点 | 口径 |
| --- | --- | --- | --- |
| 优先攻击空中单位 | 正文含该短语 | `sim.go::pickTargets` 的排序键：**嘲讽 → 空中 → 推进度** | **是排序键、不是过滤器** |
| 同时攻击阻挡的所有敌人 | 正文含该短语 | `operator.maxTarget()`：`n = max(1, len(blocking))` | 只打**她自己挡住的**，不是范围内所有人 |

两处各有一次「写成另一种会怎样」的记账：

* 空中优先写成**过滤**（`if op.spec.AirPriority && !e.IsFlying { continue }`）会让速射手在
  **没有空中单位**的关卡里一次都不出手——整关零输出。
* 「同时攻击」的 `n` 取 0 会让 `pickTargets` 空手而归 ⇒ 她在**没挡住人**的时候
  **一次都不出手**；所以是 `max(1, ...)`，不是 `len(blocking)`。
* 嘲讽排在空中之前：嘲讽是「被强制吸引」，压过一切优先规则（既有排序如此，本次不动）。

### 12.1 落点：同一条**优先链**

`sim.go::pickTargets` 的排序键现在是四段：

```
嘲讽 → 空中 → 防御力最高 → 使用远程武器 → 推进度
```

* 嘲讽排第一是既有口径（「被强制吸引」压过一切优先规则）；
* 后面三段各是一个**排序键**，不是过滤器；
* 「使用远程武器」的判据是敌人规格上现成的 `ApplyWay == "RANGED"`
  （同一字段 `sim.go:2857` 的 `enemyTarget` 早就在用，不是新造的量）。

### 12.2 ★ 行使指纹换成了**更强的那一个判据**

第二条那批用的判据是「选中的是飞行 **且** 范围里同时有地面候选」。这一批把它统一成：

> **「默认规则（嘲讽, 推进度）会选的那一个」与「实际选中的那一个」不是同一个。**

后者强得多——前者在满屏飞行单位的关卡里恒真（零信息量的绿），而后者才是
「这条规则真的插进来做了事」。三条痕迹（`TRAITAIR` / `TRAITDEF` / `TRAITRANGE`）
共用这一个判据，**只有真正改变了选择的那一次才打**。

### 12.3 站位改成**穷举路线格**（夹具构造，不是挑读数）

上一节写的是「取地面路线最密的那一格」，但实测那一格对史都华德是 0、对泡普卡才是 25。
这一节改成：**按路线密度依次试，最多 12 格，命中的那一格与试过几格一起印出来**。
判别式很清楚：站位**不是判据**，它是**夹具构造**——试格子只是把「这个时刻到底存不存在」
找出来，不是在挑一个能变绿的读数。试遍仍为 0 的，工具把**试过的格数**一起报出来。

1. `three_star_check.py` 第三趟：`main_02-09` 上试过 12 个路线格 ⇒ 0；
2. 另做一轮专用穷举：**5 个无飞行单位的主线关**（`main_01-07`／`main_00-01`／
   `main_02-01`／`main_04-04`／`main_05-03`）× **各自的全部地面路线格**（共 143 格）⇒ 0。

为什么挑「无飞行单位」的关卡：安德切尔**同时**带特性「优先攻击空中单位」与这条天赋，
而本实现把空中排在前面（见下）⇒ 只要范围里有飞行单位，那次选择就归空中那条。

**这条不是通过，是欠账**，理由是：运行期计数为 0 的机制拿不到任何证据说它做对了。
它没有被删掉，是因为删掉之后「这条还没被验证过」这件事就没人记得了——
处置与 `skill_none` 同一姿势（`check_operators_go.py::GO_ONLY_COUNTERS_ZERO_OK` 里具名登记）。

**下一步要么补夹具，要么先裁定次序**（二选一，都写在这里免得下一个人重跑）：

* 夹具方向：需要一个「**范围内同时有使用远程武器的敌人与近战敌人，且远程那个的推进度更低**」
  的时刻。本仓现有的 562 关缓存里没有找到——也许是"使用远程武器的敌人通常走另一条路、
  且不会与近战同时在同一个干员的范围内"。
* 口径方向：**安德切尔是唯一同时带两条优先规则的干员**（特性一条、天赋一条），
  「两条同时命中时谁先谁后」**没有任何取证**。本实现把**特性**那条排在前面
  （理由：不动已经上线的行为，改动面最小），但这是**选择**不是**证据**。
  裁定它等于给「特性 vs 天赋 谁压谁」定一条通则，而这条通则会影响后续所有这样的干员。

## 十三 · 【停顿】的口径裁定与落点（2026-09-25，博士裁定）

**裁定原话**：「梓兰特性的停顿与其他的相同，都是**减速 80%**」。

这条裁定**推翻**了 Go 此前的读法。此前照抄 `unit.py:1533`，
把 `sluggish_timer > 0` 与晕眩/束缚并列在推进门控的 early return 里 ＝ 按 −100% 算；
而同一份参照实现另外两处写的是 −80%（`unit.py:1065`「停顿 = 不能移动」／
`unit.py:1085-1087`「停顿降 80%：该不该乘 0.2」）——三处互相打架，这就是当初停手的原因。

### 13.1 落点两处

| 改哪 | 改成什么 |
| --- | --- |
| `sim.go` 推进门控 | **去掉** `e.sluggishTimer <= 0` 那一项（停顿不再拦推进） |
| `advance` 速度式 | 末尾乘 `e.sluggishFactor()`；无停顿时**精确的 1.0**，有停顿时 `1 − 0.8 = 0.2` |

★ **为什么末尾乘 1.0 这件事要写出来**：它是「改语义还能拿既有读数当参照」的全部依据——
没中停顿的敌人在改动前后**逐位相同**，所以只有真的挂过停顿的那几份才可能变。
实测：24 份夹具里 **10 份**挂过停顿、**3 份**判决变了、其余 **14 份零变化**（负对照）。

### 13.2 全局常数 vs 干员黑板：0.8 是**秒数**不是比例

`sluggishSlowPct = 0.8` 是**全局常数**（所有停顿都是减速 80%）；
干员黑板里的 `sluggish`（梓兰 0.8）是**持续秒数**。
出处在参照实现自己的注释里：`formula.py:585` 的 note
「**文案未给时长，数值在黑板 sluggish**」——与 `attack@sluggish`（怒潮凛冬 0.5 秒）同一条口径。

⚠ 两个数恰好都是 0.8，所以「把梓兰的黑板值当成减速比例」**不会报错**、
判决也**看不出区别**。单测里用一个不可能被误读的值（2.5）把这条钉住了。

### 13.3 顺带补上一支此前**没有任何痕迹**的机制

高台溅射挂停顿（`attack@sluggish`）此前只能经由 `POS` 那一行的 `sluggish=` 字段
侧面看见，而 `POS` 是**按名字门控**的（得先知道盯谁）。这次要回答「哪几份夹具真的
挂着停顿」，没有痕迹就只能靠猜 ⇒ 补了 `SPLASHSLOW`（打在**真的挂上**那一刻）。
实测那 10 份的计数是 2 ~ 156 次。

### 13.4 梓兰的行使见证

`tools/three_star_check.py` 第三趟：`main_00-01 @[7,3]`，`TRAITSLOW` **24 次**。
判据落在**每次出手的主目标**上（与溅射同一处、连击循环之外）——一次出手只挂一次。

### 13.5 安德切尔「优先攻击使用远程武器」：**按博士指示造了合成夹具，仍为 0**（欠账）

博士 2026-09-25 指示：「你可以自己修改一个关卡，放一个近战和一个远程进行测试」。
照做了（`three_star_check.py::synth_ranged_probe`：取真实规格、**换掉 `spawns`**，
只留手造的两只——一只近战、一只 `apply_way == "RANGED"`，同局同时进范围）。

**结果仍是 0**，而这一轮把原因钉死了：合成夹具上规则**看上去生效**
（`OPATK` 的 `pick=` 全程是远程那只 `妖怪MKII`，而近战那只 `妖怪` 同时在
`inrange=` 里、还更早到场）——但**判据 `def != pick` 不成立**，也就是说
**默认规则（嘲讽, 推进度）本来就会选远程那一只**。⇒ 那一击**不能归因给这条规则**。

造这个夹具的过程中踩到三处，逐条记下来免得重走：

1. 两只同时在场要求近战那只**打不死**（原 HP 800、每轮掉约 338，三秒就没了，
   而远程那只要 3 秒后才进场 ⇒ 两只从不同时在范围内）；
2. `wait` 段的 `progress` **照样在涨**（与 `static` 自缚同一条口径），
   所以「让远程那只先站着不动 ⇒ 它的 progress 更低」这个设计**不成立**；
3. 一次 `walk` 走完若没有后续段，敌人**当场离场**，而离场在 `pickTargets` 里是被过滤的
   ⇒ 那一刻范围里只剩远程那只，两只规则选的是同一个人。

⇒ 现状：**规则已建、归因已修对（见 13.6）、运行期见证仍未取到**。
下一步要么给出一个「远程那只的 `progress` 真的低于近战那只」的几何
（需要先弄清 `progress` 对 `wait`/单点段的定义），要么先裁定特性与天赋的次序。

### 13.6 顺带修掉一处**归因错误**（这条比上面那 0 更要紧）

原来三条痕迹的归因写成：

```go
switch { case op.spec.AirPriority: … case op.spec.PreferHighestDef: … case op.spec.PreferRanged: … }
```

它判的是「**这个干员带不带这条规则**」，不是「**这条规则是不是真的偏好选中者**」。
安德切尔同时带特性（空中）与天赋（远程）两条 ⇒ 他这一击只要重排过，
痕迹就**一律记到空中那条头上**，天赋那条的运行期计数**永远是 0**——
而那个 0 与「规则没接」判不出来。**合成夹具的第一版正是被这个错误盖住的。**

改为逐条判偏好谓词（`preferFlying` / `preferRangedWay` + DEF 比较）之后，
归因才是「这条规则做了事」。**这一条是这次真正的收获**：0 不是靠造夹具消掉的，
而是靠把归因写对才看得见。
