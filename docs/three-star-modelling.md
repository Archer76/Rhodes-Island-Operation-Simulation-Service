## 二 · 两条已有证据的结论

### 2.1 天赋的面板倍率**在权威实现里也不算**（所以这不是 Go 的账）

现算（`akdb` 只读 ＋ Go 的 `opstats` ＋ Python 的 `OperatorCalculator`）：

| 干员 | 原始面板（akdb） | 信赖 ＋ 潜能 | Go `total.atk` | Python `stats().total.atk` | 若乘天赋（×1.04）应是 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 玫兰莎 E1L55／信100／潜6 | 738 | ＋65 ＋25 | **828** | **828** | 861.1 |

⇒ **两台引擎一致地没乘**。所以：

* 它**不是**「Go 与 Python 不一致」，而是**共有的口径**：「天赋加成未应用」；
* 但按「完整建模」的要求，它**仍然是一条缺失**——`828` 与真值 `861.1` 差 4%；
* ★ 补它**必然与冻结的 Python 分道扬镳**（`ak_tactic/**` 不许改）⇒ 所有「与 Python 逐字段一致」
  的判据都要跟着改口径，这是**一个独立的决定**，不是顺手能做的。

### 2.2 技能那一支整支没接（Go 自造规格这条路上）

* `rios-sim/operators.go:100` 的 `OperatorUnported = ["skill", "active"]` ⇒ Go 压根不产出这两个键；
* `rios-sim/skill.go:83` `if sk == nil { continue }` ⇒ 技能状态机一步一步都不走；
* 实测：计划里 `skill` 写 **0 或 1，`operators[0].skill` 都是 `null`**，而闸门**两种都不报**
  ⇒ **完全静默**（判决里也看不出来）。
* 登记表那条理由（「24 份夹具 64 人次 `skill` 全是 0 ⇒ 零行使」）**在博士口径下不成立**：
  `skill: 0` ＝ 默认技能＝技 1 ⇒ 是 **64 / 64 人次都在用**。

## 四 · 纪律（写在这里，免得下一个人忘了）

1. **行使判据＝运行期计数**：`RIOS_TRACE=1` 跑一遍，看那条机制的痕迹有没有出现；
   只数「键非空／有读取点」等于零信息量的绿。
2. **修建前后对照**：每一位干员改前改后各跑一次，读数并排（本仓：控制组没红就是没有判据）。
3. **未核 ≠ 没实现**：查不了就写未核，不许写成「没有」。
4. 不许改 `ak_tactic/**`；Release 包一律不动。

## 五 · 技能那一支的**模块化设计**（博士要求：高星要能套用）

### 5.1 先量了「键词表」，因为它决定模块的边界

现算（`akdb` 的 `skill_level` 全库 1624 个技能）：

| | 读数 |
| --- | ---: |
| 全库不同黑板键 | **964** |
| **三星那 17 个技能用到的键** | **10** |
| 其中**同时在全库前 40 高频键**里的 | **10 / 10**（一个不落） |

三星用的那 10 个键：`atk`／`def`／`attack_speed`／`base_attack_time`／`cost`／
`heal_scale`／`atk_scale`／`times`／`ability_range_forward_extend`／`attack@range_scale`。

⇒ **模块化是对的路**：这 10 个键在全库的频次分别是 **399／126／119／117／90／40／288／19／21／
（`attack@range_scale` 属长尾）**——即「三星要用的键」恰好是「全库最常用的那几个」，
把「**键 → 修正**」做成一张表，三星是这张表的第一个用户，高星技能自然复用。

### 5.2 模块形态（写进代码时按这个来）

```
键驱动的效果模型（新文件 rios-sim/skilleffects.go）
  · 输入：一次部署的黑板（`skill_level.blackboard`，已由 skillmeta.go 取好）＋ 基准面板
  · 输出：① 一份「修正后的 Profile」② 一份**未识别键清单**（具名，不许静默丢）
  · 表里每一条都是：键名 → 这一条对哪个量做什么（乘／加／换）
      atk                      → 攻击力 ×(1+v)
      def                      → 防御力 ×(1+v)
      max_hp                   → 生命上限 ×(1+v)（走 Profile.MaxHP 那条既有通道）
      attack_speed             → 攻速 +v
      base_attack_time         → 攻击间隔改动
      cost                     → 开技立即 +v 费
      heal_scale               → 自疗量（按上限的 v）
      atk_scale                → 单次攻击倍率
      times                    → 连击次数
      ability_range_forward_extend → 射程前移 v 格
      attack@range_scale       → 溅射半径 ×v
  · **认不出来的键一律进「未识别」清单**并计数——覆盖账要能回答
    「这名干员这个技能，有几个键被认了、哪几个没被认」，而不是「看着像跑了」。
```

★ 验收标准（博士给的那条）：**加一名新干员不需要改判定逻辑**——
只要它的键落在表里就行；落在表外的新键**必须具名出现在覆盖账上**。

★ 这张表**同时服务天赋**：三星的天赋黑板也是同一套键（`atk`／`def`／`max_hp`／
`attack_speed`／`cost`／`atk_scale`＋`prob`），所以「天赋面板倍率族」用它同一份实现，
**不是第二套代码**。

## 六 · 天赋面板倍率族：**影响面先量出来**（决定这一步怎么做）

在做第 ③ 层之前先量影响面（`akdb` 现算，2649 条天赋行）：

| 问 | 读数 |
| --- | ---: |
| 全库有「面板键」天赋的 `char_` 干员 | **212 / 460 ＝ 46%** |
| 按键分 | `atk`×383 ／ `def`×157 ／ `attack_speed`×157 ／ `max_hp`×78 ／ `magic_resistance`×41 ／ `cost`×34 ／ `block_cnt`×23 ／ `base_attack_time`×11 |
| 三星 17 位里有这类天赋的 | **12 位**（键：`atk`×6 位 ／ `max_hp`×2 ／ `def`×1 ／ `attack_speed`×2 ／ `cost`×2） |

⇒ 三条判断：

1. **这一步必然与冻结的 Python 大面积分道扬镳**（46% 的干员面板会动），
   而 Python 侧**一个都不折**。所以它不是「顺手补一条」，而是一次**口径变更**：
   * 受影响的判据要**具名登记**（哪几套、为什么红是对的、改成什么口径）；
   * 冻的基线要**重录**；
   * 而且必须**同一笔里做齐**——只改一半会让「面板」这个量在两个口径之间摆动。
2. **做法仍走同一张键表**（`skilleffects.applyMods`）：天赋黑板与技能黑板共用
   `atk`／`def`／`max_hp`／`attack_speed`／`cost` 这批键，所以这是**复用**，不是第二套代码
   （博士要的模块化：加一名干员不改判定逻辑）。
3. **三星这一批是自然的试点**：12 位、5 个键、值都是简单百分比（`0.03`–`0.12`），
   先把这 12 位点亮并出运行期见证，再决定要不要一次推到全库 212 位。
