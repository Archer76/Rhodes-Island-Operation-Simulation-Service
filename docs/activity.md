# 活动机制完整性盘点

## 为什么单独有这一层

干员、敌人都有稳定的数据表，所以「做完了没有」可以用覆盖率回答。地图机制不一样：
**每个活动都会新引入一批装置、敌人黑板键、runes 键**，没有稳定的表可依。

于是「遇到一个做一个」有两个后果：

1. **没人知道还剩多少没做。** 一个活动跑通了、基线也对，不代表它的机制解析完了——
   漏掉半个机制与全部做完，在模拟输出上可能**完全没有区别**。
2. **漏掉的东西不会报错。** `Reborning.duration` 未被识别时，瘴与鄙瘴只是不重生而已，
   模拟照常跑完、照常出结果。

本层把「解析完整」变成**可检查的事**。

## 口径（博士 2026-09-17）

> 装置内容一定要取，不能留下未解析内容，之后每个活动的特殊机制都要这样解析完整再进行下一个。

三条落地：

- **装置内容一律取。** 装置正文常常不在库里——`trap_146_dhdcr`（天桩）的技能正文是空的，
  黑板只有一个 `branch_id`；真正的机制写在 prts.wiki 的「天桩-甲」「天桩-乙」两页上。
  取不到就去找，不能因为库内是空的就跳过去。
- **不留未解析项。** 每一项都要有明确状态：已实现、待实现（必须写来历）、或确认不需要（必须写理由）。
  不允许「不知道算什么，先放着」。
- **逐活动做完整再进下一个。** 盘点器一次给全该活动的东西，照着清单做完、把状态改掉，再开下一个活动。

## 命令

```bash
python -m ak_tactic activity act31side          # 盘点怀黍离
python -m ak_tactic activity act31side --json   # 机器可读
python -m ak_tactic activity <活动> --no-enemies # 跳过敌人黑板，快很多
python tools/check_activity.py                  # 自检
```

`--no-enemies` 会有用，是因为敌人黑板要逐只走 `EnemyLibrary`，是这一层里最慢的一步。

## 三种状态

| 状态 | 含义 | 是否影响退出码 |
|---|---|---|
| `done` | 已实现并接进模拟器 | 否 |
| `todo` | 已识别、**已写来历**，但尚未实现 | **否** |
| `none` | 确认不需要实现（必须写理由） | 否 |
| `unknown` | **未登记** | **是** |

⚠ **`todo` 不影响退出码，是故意的。** 若把「还有待实现」做成红灯，下一步必然是有人把没做的标成已做，
守卫就变成了装饰。这里的判据只有一条：**任何东西都不许处在未登记状态**——分类清楚、来历可查，
剩余工作就会出现在报告里给人看，而不是消失。

**写这段时的实测值**（会漂，用上面的命令取活的）：

```
活动 act31side：20 关、20 种敌人、3 种装置、8 种 runes、7 类黑板机制
  已实现 5 / 待实现 10 / 不需要 3 / 未登记 0
```

## 怎么保证登记表不是在自说自话

`tools/check_activity.py` 有 21 项，其中几条是防自欺的：

- 登记表的 `key` 必须与 `Entry.key` 字面相等（防止改名后判据失配）；
- 状态取值必须合法（防止写入拼错的字符串，于是那一项既不是 done 也不是 todo，静默漏掉）；
- **`todo` 项必须写了 `source`**（否则后来人拿着一个键名无从下手）；
- 盘到的装置集合必须落在登记表内；
- 已标 `done` 的装置，其常量必须真的存在（阻流阀 `BLOCKER_KEY`、泵站 `PUMP_KEY` / `PUMP_RANGE` / `PUMP_RATE`）；
- **待实现项必须仍被标为 todo**——防止有人"顺手"把没做的标成完成。

最后一条是这条纪律的守位：它不会让清单变短，它让**谎报**变难。
