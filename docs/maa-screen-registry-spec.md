# 界面登记表规范（MAA 实机驱动线）

> 适用：用 MAA/MaaCore 驱动舟游 PC 端时，**"我现在在哪一屏"** 这件事怎么登记、怎么判、怎么改。
> 位置：登记表本体是 `tmp/maamcp/stage_list_family.json`（**不入库，属运行产物**）；**规范（本文件）入库**。

## 0. 为什么需要它

一晚之内，同一个问题被答错三次：**"到了关卡列表"** 曾被判成立，而实际停在作战准备屏；**"锚帧"** 曾把一张过渡帧当稳态用，骗过一次灰带。

根因不是读错数，是**"两种不同的东西被压成一个值"**：
- **"我不认识这一屏"** 与 **"我认识它，但它是另一个"** —— 压成了同一个"不是关卡列表"；
- **"稳态帧"** 与 **"过渡帧"** —— 压成了同一个"编队屏"。

所以本规范的全部内容，就是把这两组各自拆开。

## 1. 登记表的形状

```
{
  "states": [ { "name", "role", "path", "captured", "confirmed_by", "note" } ],
  "known_non_members": [ { "name", "what", "mad_vs_X" } ],
  "transition_samples": [ { "name", "what_it_is_a_transition_of", "dist_to_anchor", "why_not_a_member", "role" } ],
  "_thresholds": { "member_below": 3.0, "grey_band_upper": 20.0 },
  "_relationship": "……各屏之间关系的文字结论……"
}
```

**三段的分工（★ 这三段判据不同，不许混）**：

| 段 | 是什么 | 判据 | 有 `role` 吗 |
|---|---|---|---|
| `states` | **一个屏** | 与同族成员 `MAD < 3.0` | 有，且必须答得出"放行后下游那步还成立吗" |
| `known_non_members` | **另一个屏** | **离成员 ≥ 39**、**自己稳定**（连拍 0.0000） | 有（如 `prebattle` / `formation`） |
| **`transition_samples`** | ★ **不是一个屏，是"正在变"** | **落在灰带（≈15）**、**连拍不稳定** | **没有，也不许有** |

★ **为什么过渡帧必须单独一段**（两条理由，缺一不可）：
1. **判据不同**：`known_non_members` 是"**稳定且离得远**"，过渡样本是"**不稳定且落在灰带**"。**把过渡帧放进 `known_non_members`，等于宣称"它是一个稳定的屏"。**
2. **`role` 的准入判据会失效**：`role` 问的是"**放行后下游那步还成立吗**"——**过渡帧根本不是"一步"，它没有下游**。**给它一个 `role`，将来有人按 `role` 放行，就会放行一个正在变的画面。**

★ **`transition_samples` 记录什么**：**"它是什么的过渡"**（例：编队屏的淡入）＋**与两端锚的距离**（例：对 `formation@D` = `15.4990`）＋**一次骗过灰带的记录**（它曾当锚用，使编队屏到关卡列表读成 `66.45`；换静止锚后为 `74.6854`）。
**它与灰带的关系是"样本"，不是"成员"。**

- `states` = **能被闸门认作"到了"的屏**（成员）。
- `known_non_members` = **已知存在、但明确不是成员**的屏。**它只作文档，不参与判据**。
- `_thresholds` = 判据的**数值口径**，写在表里而不是写死在脚本里（改口径要改一处）。

## 2. 四态闸门（判据本体）

| 判定 | 条件 | 退出码 | 含义 |
|---|---|---|---|
| **PASS** | `MAD < 3.0` **且** 最近成员 `role == "stage-list"` | 0 | 确实在关卡列表 |
| **GREY** | `3.0 ≤ MAD ≤ 20.0` | 2 | 像某个成员但不够像 —— **报警 + 定性 + 可登记**，不许压成红 |
| **RED** | `MAD > 20.0` | 3 | 不属于任何已登记屏 |
| **OTHER** | `MAD < 3.0` **但** `role != "stage-list"` | 4 | **认识它，但它是另一个** |

★ **`OTHER` 这一态是这套判据的核心**，没有它就会"与任一成员够像即 PASS"，把作战准备屏误判成"到了关卡列表"。

★ **单格不可自证**：被问"这一屏对不对"时，**把整张 MAD 表算出来**。单格读数没有参照——两个数看起来近似相等（差 0.10）时，真因可能是**参照物之间本来就只差 4.6953**。

## 3. 新屏怎么定性（三步，顺序不可换）

**第 0 步 · 静止性**（**先做这步，否则后面全白做**）
连拍 ≥3 次（间隔 ≥1 min），两两 `MAD`。**全部 0.0000 才够格当锚**。

> ★ **脚注 ·"无读数"不等于"没变化"**：看守首轮 60 s 未到时，日志里**没有那一行读数**——这是"**还没到时间**"，不是"**看了，没变**"。
> **把这两种空压成一个值，就会读成"已经确认在死等"。**
> 判据：**报告里必须分开写**——"**无读数（未到时间/未采到）**" 与 "**读到 0.0000（采到了，没变）**"。

> 反例（真实）：`drill-after.png` 与稳态编队屏差 `15.4990`，落在灰带；`diffmap` 显示 **72.08% 像素超阈、bbox 覆盖整屏、8×8 六十四块每一块都有差** ⇒ **整屏性差异，不是局部元素**；而它 `std=64.26` 明显低于稳态的 `76.71`，像蒙了一层 ⇒ 最可能是**拍在过渡/淡入途中**。
> ★ **"整屏性差异"与"局部元素差异"是两个不同的东西，必须分开判**（前者指向整屏渲染/过渡，后者指向某个控件变了）。

**第 1 步 · 定性（只定性，不取坐标）**
用读图判它是哪一类屏、抄出屏上文字、确认有无弹窗/遮罩。
★ **读图给的坐标一律不可信**（已被独立证伪两次：网格法给 HS-4 ≈ (500,600) 与三次实测不符；作战准备屏给"开始行动" (1100,690) 而 MAA 自己的 OCR 框中心是 (1178,658)）。
★ 读图**只用于定性**；**要坐标就让 MAA 的 OCR 给**。

**第 2 步 · 入族并算全表**
把它加进 `states`，然后**重算全表 MAD**，检查不变量（见 §5）。

## 4. `role` 怎么定

`role` 是**这一屏是什么**的机器可读字段，不是它的名字。

- 已知取值：`stage-list`（关卡列表）、`prebattle`（作战准备）、`formation`（干员编队）。
- **只有 `role == "stage-list"` 放行硬闸**；其它一律 `OTHER`(4)。
- 新 role 的准入：**它必须能回答"这一屏放行之后，下游那一步还成立吗"**。答不出就别给它 role —— 让它落在 `GREY`/`RED`，比给它一个假的 role 安全。

★ **同屏多态**：同一类屏可以有多个稳定状态（关卡列表实测有两个：@A 与 @B，互差 `4.6953`）。
**它们共享同一个 role，但要各占一条 `states` 记录**——因为它们是两张不同的帧。

## 5. 不变量（改表之后必须重验）

1. **两两无重合**：任何两个**不同屏**之间 `MAD ≥ 39`（实测最小的一对是 39.1366）。
2. **灰带缝宽**：`@A ↔ @B = 4.6953`。★ **它决定了 `grey_band_upper` 的下界**——**若有人想把 `grey_band_upper` 从 20.0 往上抬，先看这个 4.6953**：低于 4.7 时 @A/@B 就无法再被区分。
3. **锚的静止性**：见 §3 第 0 步。
4. **`role` 防呆不会造成假阳性**：由不变量 1 保证（不同屏离得足够远，所以"够像"只可能落在同一屏的多个状态上）。

## 6. 弃用 / 改名 怎么留痕

**不许删。** 做法是把"为什么弃用"写进登记表，并改名标注身份：

```
drill-after.png  ->  drill-after-TRANSITION-SAMPLE.png
note: ★ 上一版「编队锚」是它，已弃用；但它作为【过渡帧样本】保留 ——
      「过渡帧」本身是已证存在的现象，而它已经骗过一次灰带，
      下次遇到 15 左右的灰带可直接比。
```

★ **理由**：**知道"某个东西不能用"和知道"它是什么"是两件事**。留着样本，下一次灰带可以直接比对；删掉就只剩一句"当时觉得不对"。

## 7. 越界与盲点是两件事（动桌面之前必须分清）

"没别的办法了"**不是**动桌面状态的许可。动手前先问一句：**这个动作的后果落在谁身上？**

| | 盲点 | 越界 |
|---|---|---|
| 定义 | **不知道点了/按了会发生什么** | **可能影响本进程之外的窗口或程序** |
| 例子 | 在弹窗中央点一下（后果未知，但**限定在这个窗口内**） | **不确认前台是谁就发真按键**（键可能落进别的应用） |
| 处置 | 可以试，但要**先拍帧留底**、一次一个、事后对比 | **不许试**；要试得先**取证前台是谁**、**动作后还原**、并在报告里写明越界的范围 |

★ **"不知道"和"会影响别人"是两个维度，不能互相顶替**：**不知道后果**可以靠"一次一个 + 前后拍帧"兜住；**影响别人**兜不住。

## 8. 动桌面状态的五条护栏（实测版本）

需要把游戏窗口拿到前台时（真键盘输入的前提），**一条都不许省**：

1. **先记下当前前台**（`GetForegroundWindow` + 标题），**记进日志**——事后要能切回去。
2. `SetForegroundWindow(游戏)` 之后**必须再读一次 `GetForegroundWindow` 验证**；**不等于游戏句柄就不发键，报"聚焦失败"并停**。
   > 实测：`SetForegroundWindow` **返回 0 且前台纹丝不动**（当前前台是一个标题 `新通知` 的窗口）。Windows 有**前台锁**：**非前台进程的 `SetForegroundWindow` 会被静默拒绝**。★ **这时不要自己去绕**（`AttachThreadInput` / `ShowWindow` 最小化还原 / 按 `ALT` 解锁都会动到别的窗口状态）——**停下来问。**
3. **发键前先拍一帧**（确认画面仍是预期的那一屏、仍冻结）。
4. **只发一个键**，`KEYEVENTF_KEYUP` 要配对；发完拍帧。
5. **无论结果如何，把焦点切回第 1 步记下的窗口**，并拍帧确认。

★ **`SendInput` 的 `cbSize` 必须是真 `INPUT` 的大小**：x64 上是 **40**（`DWORD` + 4 字节填充 + 三成员联合体 32）。**只定义 `KEYBDINPUT` 会得到 32，`SendInput` 会直接返回 0。**

## 9. 收尾检查单

改完登记表，**必须**跑这六项回归，**每项单独一次裸调用**（python 不许接管道/赋值）：

| 输入 | 期望 | 退出码 |
|---|---|---|
| 关卡列表成员（`pre11.png`） | PASS | 0 |
| 作战准备（`recon1.png`） | OTHER | 4 |
| 编队屏（`pre-start.png`） | OTHER | 4 |
| 过渡帧样本 | GREY | 2 |
| 未登记屏（`pre7.png`） | RED | 3 |
| 另一个未登记屏（`now1.png`） | RED | 3 |

★ **六项要同时有 0/4/4/2/3/3 四种码**；只剩 PASS 与 RED 说明 `role` 防呆或灰带**没生效**。

★ **判据自身也会骗人**：`& $P xxx.py 2>&1 | Select-Object -Last 1` 会打印 `exit=0`——**那是管道的退出码，不是被调脚本的**，看起来像"六项全过"。**赋值同样是重定向。**
