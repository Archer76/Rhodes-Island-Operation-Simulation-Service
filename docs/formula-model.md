# 描述 → 公式模型

把干员技能/天赋/特性的**中文正文**编译成可结算的公式项。数据来源是本地库
`data/akdb.sqlite`（`skill_level.description` / `operator_talent.description` /
`operator_trait` / `module_level`），出口是 `ak_tactic/formula.py`。

> 本文是**干员侧的调研记录**，讲的是"当初为什么这么定"。
> **要动代码，先读 [`formula-maintenance.md`](formula-maintenance.md)** —— 那是写给维护者的
> 操作手册：接口清单、加一条规则的配方、必须守住的不变量、逐条踩过的坑、常用命令。
> 敌人侧见 [`enemy-formula.md`](enemy-formula.md)。

## 一、为什么非做不可

技能的实际效果有一部分**只写在正文里**，黑板拿不到：

- 赤刃明霄陈技3 的「造成 **3** 次攻击力 210% 的法术伤害」——黑板只有
  `attack@atk_scale=2.1`、`attack@max_target=4`，**没有 times**；只读黑板少算三分之二。
- 「若目标处于凋亡损伤**爆发期间**则对其额外造成…」——这是**条件性**伤害，
  黑板里只有一个孤立的 `attack@extra_ep_damage_scale`。
- 「至少造成自身攻击力 580%」与「当前生命值 6%」是 `max()` 关系，黑板给的是两个平级键。
- 「立即恢复攻击范围内所有友方单位相当于攻击力{heal_scale:#%}的生命」——
  黑板键名 `heal_scale` 有，但**回血对象与量纲**只有正文说得清。

## 二、管线

```
原文 ──normalize──▶ 扁平文本 + 槽位表 ──规则扫描──▶ [Term, ...]
```

1. **normalize**：剥掉富文本标签（`<@ba.vup>` / `<$ba.dt.apoptosis2>` / `</>`），
   把 `{key:spec}` 占位符换成单字符哨兵 `«i»` 并**记下槽位**
   （key、说明符、在文本中的位置、位数）。同时剔除 `27%（+3%）` 这类
   「潜能加成后的展示值」——它是给人看的，不能当成第二个系数。
2. **规则扫描**：规则表按**表内顺序**逐条在扁平文本上找。
   命中即**消费该区间**（已消费的字符不参与后续规则），再按 `pos` 排序输出。
   区间消费是"不重复计"的唯一保证：`攻击力和防御力+18%` 只会出一个增益项。
3. **Term**：`kind / expr / op / dtype / attr / duration / count / source /
   evidence / keys / note / pos`，`line()` 渲染成人读的一行。

## 三、量纲（最容易错的一环）

同一个数字，四种含义，**认错就错 100 倍**：

| 态 | 例 | 判据 | 渲染 |
|---|---|---|---|
| `PCT` | 正文写 `210%` | 文面自带 `%` | `210%` |
| `RATIO` | 黑板 `0.14` + 说明符 `{atk:0%}` | 说明符带 `%`，或键名以 `_scale/_ratio/_prob/_pct/_percent` 结尾 | `14%` |
| `FLAT` | `8` 秒 / `8` 点 / 2 名 | 键名在绝对值表里，或后邻字是 秒/点/格/名/个/次/层…… | `8` |
| `SCALE` | `1.4` + 后邻字 `倍` | 后邻字 `倍` | `1.4倍` |

判定顺序：文面 `%` → 说明符 `%` → 键名（比例表 / 绝对值表）→ 后邻字 → 前邻字
→ 都不成立则 `UNKNOWN`，并在该项 note 里标「量纲存疑：<键名>」。

**实测要点**：`{atk:0%}` 存的是 `0.14`，而文面的 `210%` 已经是百分数——
把后者再乘 100 就是 `21000%`。这个 bug 真的出现过。占位符键名可能与黑板
字典大小写/前缀不一致（正文 `{ABILITY_RANGE_FORWARD_EXTEND}`、黑板小写），
查表一律忽略大小写、剥掉 `@前缀` 与 `[变体]` 后缀。

535 种键的逐条判定、以及**仍未定量纲的 3 种**（3 次出现，全是装置键：
`exp` / `attack@exp` / `sell_card_gold`）见 `docs/formula-units.md`，
由 `tools/unit_audit.py` 生成（每次改规则后重跑）。
每一条待裁定的键都带 **`所属干员`**（那条例句的出处；只出现在召唤物/建筑上的键
标作 `装置「…」`）与一栏 **`裁定`** —— 该栏由人填，重新生成时会被读回续用。

**人给的量纲单独存一张表**：`formula.py` 的 `RULED_FLAT_KEYS`（2026-09-15 博士逐条
裁定为绝对值，原文写的「绝对值」与「固定值」同义）。它与从语料核出来的 `FLAT_KEYS`
**分开放**——判据的来源不同，混在一起就再也说不清哪条是谁定的。裁定原文留在
`docs/formula-units.md` 第五节的台账里，键被采纳后不会再出现在上面三节，
若不专门留档，人写的备注会随表格一起消失（`skill_max_trigger_time` 就这样丢过一次）。

拿两个已知反例说清"数据优先于裁定"：`scale_delta_to_one`（巫恋，1.3→1.8）与
`talent@prob_scaler`（红隼，1.3→2.3）被填了「固定值」，但原文都写
「提升至{…}**倍**」，按绝对值会算成"加 1.3"。这两条**没有**并入，列在该文档第六节
等复核。

## 四、规则语法

```python
_r("damage_atk",                                  # 名字：校验报告里会用到
   rf"造成相当于(?:自身|其)?攻击力{N}{PCT}{{INC}}的(?P<dt>物理|法术|真实|元素)伤害",
   "damage", op="enemy", dtype="=dt", source="ATK", scale=0, form="atk_scale")
```

- `{N}` 数值（哨兵 / literals / 中文数字 一二两三…）；`{PCT}` 可选百分号；
  `{INC}` 括号增量（`（+3%）` 整段吃掉、不计入）。f-string 里写 `{{INC}}`。
- `dtype` 三种写法：中文（`"法术"`，查表转枚举）、`"=组名"`（从文本取，
  如 `<$ba.dt.apoptosis2>凋亡损伤</>` 的类型在组里）、直接写枚举（`"ELEMENT"`）。
- `pick="last"`：系数取命中片段里**最后一个**数值。用于片段里可能夹带
  无关数字的规则，例如 `发动一次{N}连击`（"一"会被当成数字）、
  `回复…一名单位相当于攻击力{N}%`。这是一类真实错位的正解。
- `scale / scale2 / dur / count`：系数、第二系数（`max_of`）、持续、次数
  在片段数值列表里的下标；`form` 决定怎么渲染
  （`atk_scale` / `max_of` / `flat` / `signed` / `sign_down`）。

## 五、规则顺序（两条真实教训）

表内顺序即优先级，两处都踩过：

1. **元素爆发期四条规则必须排在"伤害"之前**。
   否则 `damage_atk` 会把「若目标处于凋亡损伤爆发期间则对其额外造成
   相当于攻击力 50% 的元素伤害」当成一次普通元素伤害——**条件性丢失**，
   校验看表达式还看不出来，是 `dtype` 断言揪出来的。
2. **元素损伤回复必须排在通用的"每秒回复"之前**。
   否则「每秒回复…的元素损伤」被通用的 `每秒(?:生命|回复)` 吃掉，
   产出一个系数为空的 `回复 ?`。

## 六、覆盖现状

```
语料 14967 条，命中 12513 条（83.6%），公式项 21145 个
  skill       9388/10392  90.3%
  module      1273/1531   83.1%
  trait        108/147    73.5%
  talent      1411/2233   63.2%
  trait_text   333/664    50.2%
```

（语料比生息演算剔除前少 469 条——该模式的装置与其专属技能已不入库，
见 `docs/operator-db.md`；命中率因此从 81.8% 升到 83.6%，分母里原本有一批
永远命不中的建造评分/能源值文本。）

**残句政策**：只补战斗相关句式。生息演算（兽栏/建造评分/能源）、
「主动开启技能，与该角色对话」、基建与剧情文案**一律不补**——
它们不影响战斗结算，补进去只是污染。

仍高频且战斗相关的残句（待补）：拖拽期间正比于距离的法术伤害、
「技能开启时普通攻击会造成法术伤害」这类攻击属性改写、
浮游单元叠层、火环/灼烧地段的逐秒结算、无人机召唤物的存库与销毁。

## 七、校验

`python tools/check_formula.py`（100 项），七节：

1. **锚点**：具体句子必须解出指定公式（赤刃技3 取大式与 3 连击、怒潮凛冬
   括号增量、四类元素损伤、量纲三态、`发动一次{N}连击` 取最后一个值、
   区间消费不重复）。
2. **库内端到端**：从 `data/akdb.sqlite` 读原文+黑板再解析一遍，
   防止「语料加载」与「直接调用」两条路径分叉。
3. **量纲不变量**：未定量纲的键 ≤30 种、出现 ≤600 次、混合量纲 ≤2 种、
   靠上下文判定的出现次数 >2000，以及 `Num` 的单值断言。
4. **覆盖率下限**：按来源设下限，规则被改坏会立刻掉下来。
5. **结算层**：`FormulaEffects / compare_effects / merge_effects` 的定点值
   （取大式不许当倍率、连击作用域、缺键不算分歧、`merge` 不许改黑板有值的
   字段、`desc` 才按描述改）。
6. **算式解析器**：见 `docs/enemy-formula.md` 第五.7 节。
7. **干员侧属性词补齐（不接算式 pass）**：见下。

`tools/check_battle.py` 的第 [10] 节则从**战斗结果**这一侧验收同一件事。

### 7.1 干员侧为什么不接算式 pass（2026-09-16）

博士的裁定是「**全部接入，本项目之后需要脱离 llm，不能保留自然语言**」。
我原本建议不接，理由是收益低；实地量完之后发现**理由比"收益低"更硬**：

干员语料（14967 条）里能被 `find_exprs` 抓到的片段有 **395 个**，逐个看过，
**没有一个是真算式**。它们分两堆：

* **223 个**是 `攻击距离+1`、`浮游单元+2`、`攻击目标数+1` 这种形状——
  看着像代数式（变量「攻击距离」加 1），**实际是属性增益**。接上去只会得到
  `算式 攻击距离+1 ⟨变量：攻击距离⟩`：形式忠实、语义全错，而且**比不收更糟**
  ——它把「没认出来」伪装成「已经解析」。
* **172 个**是 `每使用过一次技能额外追加攻击力+20%`、`"微尘"上限+3`、
  `敌人被击倒时转移至目标周围最近的其他敌人并使剩余攻击次数+1` 这类
  **散文里夹了个 `+1`**，连形状都不是算式。

根因是**正文来源不同**：敌人侧来自 prts.wiki 的**人手写的 wikitext**，真会写
`移动速度+(50%×加速层数)`；干员侧来自 gamedata 的**游戏内正文**，一律是
`属性+N` 记法。所以：

* 服务裁定的**目标**（不留自然语言残句）要落在**规则**上，不是落在钩子上。
  本轮补了 `攻击距离` / `攻击目标数` / `浮游单元` / `最大生命值` 等属性规则，
  未被规则消费的「`裸词±N`」从 **756 处降到 371 处**，且剩下的大半是
  `能量数+1`、`TOKEN数+3`、`技力+1` 这类**计数器**——既不是属性也不是算式，
  本来就该留在外面。
* `check_formula` 里钉了一条 `干员侧不得产出 expr_var`：算式钩子只挂在
  `enemy_formula.parse_enemy`，干员侧走裸 `parse`。**用计数当断言是错的**
  （计数器数量不少，钉在计数上只会逼后来的人为了过测试去乱收），
  结构不变量才守得住。

## 八、驱动战斗结算（已接入）

`battle/sim.py` 的 `effect_source` 三个取值，都建立在黑板之上，区别只在**描述
那一路走多远**：

| 取值 | 含义 |
|---|---|
| `blackboard` | 只用黑板（外加 `skill.py` 里原有的两条描述钩子：真实伤害、`造成 N 次`）。旧行为，用于回归对照 |
| `merge`（默认） | 再用完整的公式模型补黑板的**空缺**：攻击力倍率、连击数、治疗倍率、元素损伤。黑板有值时一律以黑板为准 |
| `desc` | 结算只信描述（黑板仅作兜底），用于敏感性分析 |

落地位置：`SkillLevel.formula_effects()` / `resolved_effects(policy)`（惰性缓存）
→ `sim._attach_skill` 按策略解析并挂到 `OperatorUnit.effects_override` →
`OperatorUnit.effects` 优先返回它。

**为什么不默认 `desc`**：黑板是引擎真值，描述是给人读的。全库 911 条技能行里
两者在 `atk_scale` 上一致 257 条、真分歧 6 条、描述独有 42 条——那 6 条必须
逐个人看，不能拿默认值去赌。

**连击必须分作用域**（本轮最重要的一个修正）：全库 49 条"只有描述才有的连击"
混着两类写法——

* 「**每次攻击**对最多 4 名敌人造成 3 次…」（赤刃技3）→ 改写的是平A，**该并**；
* 「对**范围内**的所有敌人造成 2 次…」（德克萨斯技2）→ 技能自己的一次性范围
  多段，**并进来会把平A也翻倍，是假的**。

判据取 `Term.context`（命中位置之前 18 字）+ 规则名：42 条判为 `attack`、
9 条判为 `skill`、4 条判不了（**不并**，宁可少算）。最终 38 条技能的战斗行为
因此改变。

**实测效果**（`check_battle` 第 [10] 节，1-7 单干员芳汀技1「攻击变为二连击」）：

```
blackboard  139.5s  击杀 34  漏怪 7  总伤害 48,850
merge       141.0s  击杀 36  漏怪 5  总伤害 54,900
desc        141.0s  击杀 36  漏怪 5  总伤害 54,900
```

黑板路径少算约 12% 的伤害、多漏 2 只——因为 `times` 只写在正文里。
SR-EX-8 的四人方案在 `merge` 下与旧基线**完全一致**（219.8s / 38 杀 / 1 漏 /
剩 2 命 / 总伤害 1,501,148），说明这一层没有扰动已验证的战斗基线。
（此处是 2026-09-16 把剑气速度改为录像实测值 1.2 格/秒之后的口径。）

**尚未结算的部分**：元素损伤只走到"记录"这一步（写进 `SkillEffects.other` 的
`ep_damage@凋亡` 等键），还没有损伤条与爆发的结算——模拟器目前没有这条轴的
模型，需要新增（累积阈值、爆发窗口、爆发期元素伤害、损伤回复）。
