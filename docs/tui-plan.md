# 终端界面（TUI）方案

> 立项 2026-09-17。**选型已定，流程按博士四步要求改写**。本文件是实现前的依据，不含实现。

## 一、它是什么

不是「浏览器」，是**一次向导式流程**：启动 → 检查登录态 → 选关卡 → 指定部分编队 → 解算（带进度）→ 输出并导出 MAA 作业。

## 二、四步流程

```
启动
 └─[0] 登录态自检 ── 不可用 ──> 引导重新提供登录态（可跳过 → 降级为手输练度）
        │可用
 └─[1] 选关卡        ── 从本地关卡表里选（SR-EX-8 这种）
 └─[2] 指定编队      ── 可跳过；只指定一部分，其余由解算补
 └─[3] 解算          ── 进度条 / 人数 / 已试组合 / 耗时
 └─[4] 结果与导出    ── 展示通过的成员 + 模组 + 技能，确认后写 MAA JSON
```

## 三、[0] 登录态自检（**本轮最重要的实测结论**）

### 必须打 `game/player/*`，不能打 `user/check`

2026-09-17 实测，本机 `~/.skland/cred.json` 的实际状态：

| 端点 | 结果 |
|---|---|
| `/api/v1/user/check` | `code 0`、`message OK`、还能返回昵称 |
| `/api/v1/game/player/binding` | `10000 请求异常` |
| `/api/v1/game/player/info?uid=…` | `10000 请求异常` |

**cred 已经读不了游戏数据了，而 `user/check` 照样回 OK。** 用 `check_cred` 判可用性会给出**假阳性**——TUI 会在「看起来已登录」的状态下走进第 1 步然后崩掉。`tools/skland.py status` 现在正是这个形态：先打印 `check: OK`，再在取绑定列表时失败。

排除项（都试过，均非原因）：
- **不是签名配置**。照抄一图流的 Web 配置（`platform:"3"` / `vName:"1.2.0"` / `dId` 用 UA 字符串）与项目现有的安卓配置（`platform:"1"` / `vName:"1.45.1"` / 数美指纹）**结果逐字相同**。
- **不是参数**。缺 uid 时 `player/info` 回 `10001 参数错误`（说明已过鉴权、进到参数校验），带 uid 后回 `10000`。
- 排除 `/web/` 前缀（404，`/api/` 是对的）。

**结论：自检端点用 `game/player/binding`。** 仅当它回 `code 0` 才算登录态可用。

### 不可用时的两条补登录路径

**博士已裁定：不用短信、不做扫码，剩下两条平铺并列，不分优先级。**

| 方式 | 用户动作 | 状态 |
|---|---|---|
| **森空岛凭证** | 在森空岛网页控制台复制 `localStorage` 的 `SK_OAUTH_CRED_KEY,SK_TOKEN_CACHE_KEY` 粘贴 | **本轮实现**，且不需 dId / 数美指纹 |
| **官网 Token** | 在 `ak.hypergryph.com` 复制 token 粘贴 | **本轮实现**——`hgToken→cred` 代码已有（`save_cred` 的 `hg_token` 阶段），**只缺粘贴入口** |

去掉的两条：

- **手机号 + 短信验证码**：不进 TUI。（`tools/skland.py` 的 CLI 仍保留该入口——那是工具链的事，与界面无关，且自检要用。）
- **扫码**：**不做，也不逆向**（博士裁定 2026-09-17）。曾经查到的线索一并作废，不再作为待办：一图流的二维码握手在它自家后端（`/survey/skland/qr/create`、`/survey/skland/qr/check`），zonai 与 as 上的候选端点全部 404。

另有一个**不属于并列选项**的出口：`Esc` 跳过登录，降级为手输练度。理由见第七节的降级路径。

### 凭据生命周期：尽可能久地保存登录态

**博士要求：尽可能久地保存登录态，减少频繁重登。**

#### 病根：现在根本没存住

实测本机 `~/.skland/cred.json`：

```
cred / token / userId      ← 只有这三个
hgToken = None             ← 唯一的长效凭据是空的
无时间戳、无 stage          整个文件 148 字节
```

当初走的是短信链路，只落了短命的 `cred`，把能反复换 cred 的 `hgToken` 丢掉了。**这就是"过期只能重来"的直接原因**——不是 cred 天生短命，是我们没留下能续它的东西。

#### 两条路径的耐久度并不相同（这一条必须让用户看见）

| 方式 | 拿到什么 | 过期后 |
|---|---|---|
| **官网 Token** | `hgToken`（鹰角通行证 token） | **可静默重换 cred，不必再问用户** |
| 森空岛凭证 | `cred` + `token` | 没有再换的凭据，**只能重来** |

**「尽可能久」这个要求实际上只有官网 Token 那条能满足。** 所以两条虽然平铺并列，但界面里**每条都要标注耐久度**，否则用户会挑更省事的那条（粘贴森空岛凭证），然后两天后再来一次——与「尽量少重登」的目的正好相反。

#### 落地设计

1. **凭据文件升级**：加 `savedAt` / `credAt` / `hgTokenAt` 时间戳与 `stage`；**`hgToken` 一旦拿到就必须落盘**。没有时间戳就无法区分「陈旧但可续」与「已死」，只能一律重登。
2. **启动时的三段式判定**（不是「可用 / 不可用」二值）：
   - ① 打 `game/player/binding` → 通 → 直接进流程
   - ② 不通、但**有 hgToken** → **静默重换 cred**（用户无感），再打一次
   - ③ 仍不通，或**没有 hgToken** → 才请用户提供
   第 ② 步是「减少频繁重登」的全部要害——**绝大多数过期都能在这一步无声消化**。
3. **名册缓存兜底**：`data/skland/roster_<uid>.json` 已存在（本机 197 KB，9-15 13:11）。练度变化很慢，**登录态不通时用上一次的名册并标注新鲜度**，比硬失败好得多。这样即便 cred 彻底死了，选关与解算仍可继续。
4. **不主动过期**：只在真正调用游戏端点失败时才判定失效，不做「N 天前用过就要求重登」这类自作聪明的策略。

#### 未知量

**cred 的实际 TTL 未知。** 现有唯一样本：9-15 13:10 取得，9-17 已不能读游戏数据（`binding` 回 `10000`），故 **≤ 约 2 天**。而 `hgToken` 的 TTL 同样未知。**这两个数都该在拿到 hgToken 后实测记录**，否则「多久该续一次」只能靠每次调用失败来发现。

已排除的原因（都不是）：不是签名配置（Web 与安卓两套结果逐字相同）、不是参数、不是 `/web/` 前缀。**线索：skland 官网前端有 `/web/v1/auth/refresh`**，将来若要做「更久的续期」可以从这里入手。

## 四、[1] 选关卡 —— 关卡名列表要新建

**现状：项目没有持久化的关卡名列表。** 实测：`akdb` 的 14 张表（operator / skill / module / tile / attack_range…）与 `enemydb` 的 5 张表里**都没有关卡表**；关卡索引只存在于 `data/gamedata/_level_index.json`——那是**缓存**，`data/gamedata/` 已 gitignore、文档明说「约 17 MB，可随时删」、TTL 7 天。

**清一次缓存或断网，关卡选择列表就没了**，所以必须落到持久的地方。

索引内容（实测）：4694 条、2227 个去重 `code`，含 `SR-1`～`SR-8`、`SR-EX-1`～`SR-EX-8`、`SR-TR-1`；带难度档 NORMAL 3503 / FOUR_STAR 1014 / RUNE 132 / SIX_STAR 45。

### 已裁定：单独拉取并建库，仓库内不放数据文件

**博士裁定（2026-09-17）：仓库内不放数据文件；关卡名与干员、敌人数据同样处理——单独拉取、建库。**

这与项目现有的合规依据严丝合缝：仓库「不分发任何第三方内容」（被跟踪文件里没有任何 .json/.sqlite/.csv），数据一律构建时取回、落 gitignore。

**落点：`akdb` 的 `stage` 表。** 理由三条：

1. 同源已有先例——`akdb` 现有的 `tile` 表（95 条）就走独立的 `db tile-fetch`，来源是 theresa.wiki，并非 gamedata；
2. 关卡索引与干员数据同属「游戏本体」一侧，与敌人库那套（prts.wiki，口径相反、必须建库时算好继承）不是一类；
3. 少一个库文件、少一套 schema 版本沿革。

若博士更想要独立文件（`stagedb.sqlite`），迁移成本很小——把 schema 与 API 挪出去即可，故不作为阻塞项。

#### 落地要点

- **单独取数**：`level_index.json` 的来源是 `map.ark-nights.com` 首页 → 正则取 `bundle.<hash>.js` → 拉 bundle（约 7 MB）→ 扫所有 `JSON.parse('…')`，取「最长的、且每个值都含 `data_path` 的字典」。现有实现在缓存层，**要把它提升为建库的取数源**。
- **命令**：仿 `db tile-fetch`，新增 `db stage-fetch`（取数 + 写表）；`db build` 保持**不联网**的既有性质，不被这条破坏。
- **表内容**：`levelId`（主键，如 `act54side_ex08`）、`code`（显示名，如 `SR-EX-8`）、`difficulty`（NORMAL / FOUR_STAR / RUNE / SIX_STAR）、`zone_id`、`data_path`。同 code 会有一条 `#f#` 后缀的四星限定版，**主键必须是 levelId 而不是 code**。
- **版本**：`DB_VERSION` 5 → 6，两个库都要重建核对（`db build` 与 `enemydb build`）。
- **取数失败的行为（博士裁定 2026-09-17）**：**明确输出「关卡名获取失败」**，并**保留上一版表**（绝不写空表）。同一口径适用于干员与敌人数据——取不到时分别输出「干员数据获取失败」「敌人数据获取失败」。
  - 这与 `tile` 表的既有行为**不同**：tile 取不到只记一条警告、表留空。关卡表**不能沿用**这个写法——空表会让用户以为"这游戏没有关卡"，而不是"这次没拉到"。
  - 提醒文案**必须能用 GBK 编码输出**。`db/build.py` 里已有先例注释：「用「警告：」而不是 ⚠：Windows 控制台是 GBK，编不出的字符会让…」。
- **自检**：进 `check_db.py`（akdb 的自检），断言条目数量级、`SR-EX-8` 能按 code 查到、主键唯一，以及**取数失败时表未被清空**。
- **缓存 TTL**：索引的缓存 TTL 现为 7 天，与「建库」是两回事——表一旦建成即持久，TTL 只管取数时是否重拉。

#### 只取这五类（博士 2026-09-18）

`zone_table` 有 477 条、11 类。**只留** `MAINLINE`、`BRANCHLINE`、`CAMPAIGN`、`MAINLINE_ACTIVITY`、`ACTIVITY`——口径就是 [theresa.wiki/map](https://theresa.wiki/map) 的分类（两边的类型名与逐类条数完全对得上）。其余六类（肉鸽 6、爬塔 24、周常 9、导览 1、`SIDESTORY` 84、`MAINLINE_RETRO` 3）**既不进库也不进菜单**。

| 项 | 裁定 |
|---|---|
| 判据 | **两条数据关系**，不是 id 前缀：① `zone.type` 在白名单里；② 关卡的 `zone_id` 在 zone 表里查得到 |
| 为什么第二条也要 | 它一次覆盖两类东西——被剔除类型下面的关卡（肉鸽 696、爬塔 236、周常 35、导览 2），以及 `zone_id` 指向一个 zone 表里**根本没有的** zone 的关卡（干员密录 `mem_*` 308、生息演算 `sandbox_*` 159、危机合约 128、小玩法 25、活动旧 id 64…）。这些本来就进不了菜单，博士裁定一并清掉 |
| 落点 | 写入口径在 `insert_stages`（筛行 + 同事务清库）；`db stage-prune` 可单独清（**不联网**，带 `--dry-run`）；`db stage-fetch` 每次重取都会顺带清 |
| 实清一次 | 127 个 zone / 1660 关 → 留下 350 个 zone / 3034 关 |
| 活动名 | 去掉「复刻」后缀（43 个里 42 个写 `墟·复刻`、1 个写 `不义之财 复刻`）。判据是**后缀**，`玛莉娅·临光` 这类带间隔符但不带复刻的名字不动。改名不会让菜单出现重复条目——**活动复刻后原版的 zone 就不再有关卡了**，一对里只有一条进得了菜单 |
| 菜单位置 | 主线各章 → 第 15–17 章（`MAINLINE_ACTIVITY`，那也是主线，必须紧挨着）→ **剿灭作战** → 插曲·别传 → 活动 |

**`CAMPAIGN`（剿灭作战）的显示名得自己造**：它的 15 个 zone 在 gamedata 与 theresa.wiki 里名字**全是空的**（取数只到 `zoneNameSecond: None` 这一层），所以整类归成一条「剿灭作战」，分部名取该分部里关卡的**关卡名**——`龙门外环、龙门市区、龙门商业街`。这也是唯一有意义的取数：15 个分部的关卡名两两不重复，天然不会撞名，而玩家认的就是图名。分部的先后按 `zone_id` 尾号（它们的 `zone_index` 全是 0，只按它会退化成字符串序 1、10、11…2）。

**`BRANCHLINE`（插曲·别传）为什么暂时在菜单里看不到**：它是 20 个 `permanent_sub_N_zoneM`——**永久开放入口**，分部名与活动本体一一对应（`格兰法洛`/`失落旗舰` 对应愚人号，`漫漫独行`/`浩瀚之旅` 对应遗尘漫步，`阵中往事`/`破败前线`/`战火回想` 对应生于黑夜……）。关卡索引把那些关挂在**活动**那一侧的 zone 上，所以这 20 个 zone 自己一条关卡都没有，拼不出菜单条目。**内容没丢**——它们以活动名（愚人号、遗尘漫步、生于黑夜…）照常出现在菜单里；自检里有一条就守着「那 20 个分部名在菜单里都找得到」。

#### 主线标题的写法（博士 2026-09-18）

菜单第一层里主线各章写成 **`第X章　章节标题`**（`chapter_label()`，中间是全角空格），副标题取 `name_second`：

| 行 | 显示 |
|---|---|
| 序章 | `序章　黑暗时代·上` |
| 第一至十四章（`MAINLINE`） | `第七章　苦难摇篮`、`第十四章　慈悲灯塔` |
| 第十五至十七章（`MAINLINE_ACTIVITY`） | `第十七章　相变临界`——`name_first` 是英文，章号仍按 `name_title` 拼中文数字 |
| 活动 / 剿灭作战 / 插曲 | **不套这个格式**，照旧走活动名或分部名 |

**博士原话是「改成【第X章 ’章节标题‘】」，而书名号与单引号只是他写格式说明用的记号，不是要印在屏幕上的字**——他随后澄清了这一点。所以屏幕上没有 `【】`、也没有 `‘’`；自检里有一条正面守卫钉住这件事。

反面同样要守住：**活动名里自带的引号不许动**（「“下井”」「“林”中漫游」是上游名字的一部分，不是我们加的排版）。这两条一开始被写成同一条「标题里不许有引号」，结果被真实活动名当场证伪——**判据的适用范围要跟着"这段字是谁写的"分**，不能一刀切。

`zone_title()` 保持旧口径（分部名与 `list_zones` 还在用它，第 1-14 章仍只给章号），两处的章号共用 `_chapter_head()`，免得哪天漂开。原来只写章号的第 1–14 章因此补上了副标题——这也是博士这条要求的实质。

判据在 `tools/check_tui.py` 的 `check_stage_layers()` 与 `check_stage_categories()`。


## 五、[2] 指定编队（可跳过）

只指定**一部分**成员。跳过时走全自动。

**两种模式（博士 2026-09-17 追加）：**

| 模式 | 含义 |
|---|---|
| **只用我选的这几个** | 候选池 = 用户选中的集合，**程序不得引入其他人** |
| **允许程序补充**（默认） | 候选池 = 用户选中的 + 名册里其余人 |

**这两种模式不需要新增搜索能力。** `Searcher.search(stage_id, roster, operators, ...)` 本来就收一个 `operators` 序列当候选池（`ak_tactic/search.py:292` / `:397`），两种模式只是**池子怎么拼**的差别，界面里做成一个开关即可。

**候选池大小（`AUTO_POOL = 24`）是内部量，不进界面**（博士 2026-09-18）：「编队人数部分只写使用了几人编队」。24 是**从哪里挑人**（候选池），与**出战几个人**是两件事——原先编队屏写「不够的补到 24 人一起挑组合」，读起来像"要带 24 个人上场"。现在这一屏只说「你勾的人优先；不够的程序从名册按练度补人来挑组合」，池子多大只在解算日志里以一句带说明的话出现（「这是程序挑组合的范围，不是出战人数」）。

**助战（+1 位）暂不考虑**（博士 2026-09-18）——作业里的助战位与好友协议都得另立一层，先不做。

### 两行分类：主职业行 + 子职业行（博士 2026-09-18 的图与三条裁定）

上图定稿的编队屏是**两行分类**，不是一颗 `G` 键循环分组（`G` 已于 2026-09-18 去掉，见下）：

| 行 | 内容 | 行为 |
|---|---|---|
| 主职业行 | 最左「**全部**」+ 名册里真有的主职业（按游戏顺序，不列 `TOKEN`/`TRAP`） | **默认停在「全部」**；停在「全部」时**子职业行整行不显示**；选中某个主职业后子职业行才出现 |
| 子职业行 | 「全部」（＝这一职业下不再筛）+ **该职业所有的**子职业（名册里有的，按练度序） | 点/方向键走动即生效 |

三条裁定里另两条：`(initial)` 要自行核查（**已查清**，见下）；行首那个 `x` 是 Textual 自带的选中样式，不改。

**`G` 键去掉的原因**（博士 2026-09-18 原话：「选人界面可以去掉按 G 切换分类的功能了，与新加上的筛选重复」）：原先 `G` 在「列表表头按主职业」与「按主职业·子职业」之间循环。现在**子职业是靠子职业行筛的**，表头再按子职业分一次组只是把同一件事说两遍——筛到某个子职业时，列表里那几十行表头还是同一行字。所以表头**固定按主职业**，`D.group_label()` 也不再接 `mode` 参数（留着它就会有人以为界面还能切）；顶上那行说明里的「分组：…」一并去掉，剩下 `范围 / 练度 / 筛出 / 已勾`。自检里留了一条反向守卫：**按一下已去掉的 `G`，组数与勾选都不许变**。

**`equipped_status` 有三个取值，只有 `ok` 是"装了正经模组"**（核过本机名册 211 人：`ok` 196 / `initial` 13 / `special` 2）：

| 取值 | 是什么 | 例（本机名册） | 界面写法 |
|---|---|---|---|
| `ok` | 已生效的模组，有等级 | 圣聆初雪 `uniequip_002_sbell2` Lv3 | 「模组3」 |
| `initial` | **初始证章**（`uniequip_001_*`，名字以「证章」收尾，**没有战斗数值**） | 德克萨斯「德克萨斯证章」 | 「初始证章（不加数值）」 |

以前把非 `ok` 的取值**原样印成英文**，界面上就是 `(initial)`——玩家看不懂，而它其实是"这位身上只有一个不生效的证章"。

**分类行为什么不用 `Tabs`**：`Tabs` 排不下就**横向截断**，而中文是双宽字符——近卫一族 14 个子职业加上「全部」，光名字就是 78 列，80 列的窗口里最后几个看不见、方向键也够不到（实测 `_proto/squad_rows_probe.py`：80x20 下「武者 本源近卫 佣兵 重剑手」落在行外）。改成自己折行（博士已定：「子职业放不下的话可以分两行」）：80 列折成 2 行、120 列 1 行，命中判定与渲染用同一份布局，第二行上的项照样点得到。

**终端里没有"字号"**：图上主职业行是大字，终端做不到——能做到的是字重与留白，所以那一行是「加粗 + 上下各留一行 + 项间空两格」。矮窗口下留白让路（`Screen.compact`），顶上那句说明收成一行，80x12 里两行分类 + 列表 3 行仍然全在可见区内。

### 这一屏踩过的三个坑（都留了守卫，别再踩第二次）

| 症状 | 根因 | 现在的做法 |
|---|---|---|
| 点分类行的位置与高亮对不上 | 布局按 `gap` 推进坐标、`render()` 却没把那几格空格写进 Text，于是第 k 项偏 `k*gap` 列 | **算进去的列必须真的画出来**；判据从渲染出的字符串里数（`check_tui` [12b]「格子坐标 = 画出来的列」），不从布局里算——自己算就是自证自洽 |

## 六、[3] 解算的进度反馈

**现状：`ak_tactic/search.py` 没有任何进度钩子**，只有 `verbose` 布尔。所以进度条需要先给搜索加一个回调/生成器接口，UI 才能拿到「已试多少组合 / 当前最优 / 已用时」。

**这是全案唯一一处需要动核心代码的地方。** 回放屏砍掉之后（见第十节「回放屏为什么去掉」），`battle/sim.py` 完全不用碰，那条优化到 1.18× 的热路径保持原样，三关基线（1-7 / SR-6 / SR-EX-8）的可比性也不受影响。

### 已裁定（2026-09-18）：出战人数以**关卡可部署人数**为准，默认 4 人起、找不到就自动加深

博士原话：「关卡可部署人数要接进来默认还是 4 人，找不到的情况就做自动加深，但编队 12 人上限和可部署人数不冲突——是可以撤下不使用的干员换上其他人的」。

三件事因此定下来：

| 项 | 取值 | 出处 |
|---|---|---|
| 搜索深度**上限** | 这一关的**可部署人数**（`options.characterLimit`），不是写死的 4 | `Searcher.deploy_limit()` 读 `Verifier.stage()` 已加载的那份关卡（同一实例内是内存命中，不额外联网） |
| 深度**起点** | 4 人 | 大多数关卡 4 人就够，先花最少的钱试一次 |
| 找不到三星时 | 按 **+2** 自动加深，直到可部署人数为止；阶梯末端一定落在上限上（上限 8 → `[4, 6, 8]`） | `depth_ladder()` |
| 12 人 | 只是**编队槽位**的封顶，与可部署人数不冲突 | 撤下不用的干员换上别人即可，所以真正的闸门是可部署人数 |
| 取不到可部署人数 | 按 12 封顶，并在日志里写明原因 | 悄悄按 12 搜会让人以为这一关真能上 12 个 |

实测本机四关（1-7 / HS-EX-4 / HS-EX-5 / SR-EX-8）的可部署人数**都是 8**，所以阶梯是 `[4, 6, 8]`——最坏情况要跑三轮。

**这也解释了 HS-EX-4 的 214 秒**：候选池 24 人 × 每人 6 个落位 = 144 个候选，每层 beam 5 → 720 次模拟，深度往上还要重跑浅层。加深会让它更贵，所以**性能是下一步的硬需求**（见第十一节）。

界面上这一屏只写「本轮最多 N 人」与「本关最多可部署 M 人」——都是**出战人数**口径，与候选池无关。

## 八、技术选型：Textual（已实测）

参考 `gh` CLI 的 TUI，Python 侧对位：`bubbletea` ↔ Textual `App`，`lipgloss` ↔ Textual CSS，`bubbles` ↔ Textual widgets；`gh-dash` 那种「顶栏 / 中列表 / 右预览 / 底按键栏 / `?` 帮助」可直接照搬。

2026-09-17 在 Python **3.14.4** 实测：依赖干净解析（textual 8.2.8 + rich 15.0.0 等 9 包，均 MIT 系）；**无 tty 下 `run_test()` 能建界面并渲染**（这条是能否进自检体系的关键）；文本快照出口是 `_compositor.render_strips()`（CJK 宽度算对）。

**五处 API 漂移**（Textual 8 与网上 0.x/1.x 示例差距大，均实测）：
1. CSS 里 `border-title: 中文;` 被拒 → 面板标题走 `widget.border_title` 属性
2. `DataTable.cursor_type` 默认 `"cell"` → `RowHighlighted` 永不触发，列表必须显式设 `"row"`
3. `add_row` 不传 `key=` 时 `row_key.value` 是 `None` → 行键必须给领域主键
4. 焦点必须显式给（`table.focus()`），`pilot.press` 只发给聚焦控件
5. `Static.renderable` 与 `export_text()` 在 8.x 已不存在

**依赖纪律**：`textual` 必须在 `tui` 子命令内部**惰性导入**，其余 15 个子命令保持零依赖可离线运行；缺包时给人话并返回非 0，不抛 traceback。

### 中文输入法：字母键会被吞（实测）

**结论：中文输入法（半角）状态下，字母键根本到不了程序**——它们被输入法拿去做
候选字了，Textual 收不到任何键事件。这不是本项目的 bug，在终端里也修不了；
用户按 `Shift` 切到英文即可。`Enter` / `Esc` / 方向键不受影响。

**但全角字符是可以修的**，而且原先确实是坏的：全角模式下按 `l` 送过来的是
`ｌ`（U+FF4C）、按 `1` 送的是 `１`（U+FF11），与半角是两个字符，
按键匹配表里一个都不命中——**界面上写着 `L`，按下去毫无反应**。
`both_cases()` 现在给每个单字符键补全角孪生（`+0xFEE0` 那一批），
`AskScreen` 的 `1`–`9` 也走同一张表，所以全角数字同样能选。
判据在 `tools/check_tui.py` 的 [16] 节：真按 `ｌ`、真按 `ｓ`、真按 `１`。

### 扫码为什么又回来了

早先裁定过「直接去掉，不逆向」，那是针对**逆向森空岛客户端**那条路。需求第 11 条要求「这次测试加上登录测试」之后走的是**官方**三步：`general/v1/gen_scan/login` → `general/v1/scan_status` → `user/auth/v1/token_by_scan_code`，都在 `as.hypergryph.com`，**三步都不需要 dId**（dId 只到最后一跳 `generate_cred_by_code` 才用，本项目用数美换真值）。

拿到的 `hgToken` 与官网导出的 `data.content` **是同一类凭证**、进的是同一个 `grant()`，所以扫码**既方便又耐久**，且完全避开「官网 Token 敏感度不亚于账号密码」那一层风险。三条路的耐久度排序：**扫码 = 官网 Token > 森空岛 `cred,token` 粘贴**。

### `Esc` 逐层返回：为什么它需要一个「路径」才做得成

向导里每一屏选完是 `dismiss(值)` 把**自己**弹掉的（弹出时触发回调，回调再推下一屏）。所以屏幕栈里**始终只有当前屏**——上一层早就不在了。于是 `pop_screen` 退不回上一层：在关卡层按 `Esc` 会一路掉回主界面。

修法是让 App 自己记一条**路径**（`RiosApp._path`）：`push_step(make, callback)` 压一屏的同时把「怎么把它重建出来」追加到路径尾，`step_back()` 丢掉尾巴（自己）之后把新的尾巴重新推出来。

**两个容易写错的地方**（都踩过）：

1. **不能把被弹掉的那一屏再推回来**。早先的写法是「弹出路径最后一格 → 用这一格推回去」，结果**按一次 `Esc` 什么都不变、要按两次才退一层**——弹掉的正是当前这一屏，推回来的还是它。正确做法是先丢自己、再推上一层。
2. **解算屏不在路径上**（它是 `push_screen` 直接推的），所以它的「中止」不能走 `step_back()`，要走 `back_to_step()`——只把路径顶格推出来，不丢任何东西。

守卫在 `tools/check_tui.py` 第 [15] 节，**真跑一遍向导、真按 `Esc`、再看落在哪一屏**（关卡层 → 选分部 → 选章/活动 → 准备屏）。只看 `BINDINGS` 表**测不出这个 bug**：每一屏都规规矩矩挂着 `escape → back`，而行为是错的。

### 账号模型：为什么凭据要按 uid 分文件

博士 2026-09-17 给了两个要求——「初次干净启动先进入登录向导」与「加一个退出账号的功能方便切换账号」——它们合起来逼出了这个模型。

**`Esc` 是「不登录」，但"不登录"有两种。** 一次性的与永久性的后果差得很远，所以要在那一按之后补问一句。写进配置的只有「以后都不登录」；选「本次」什么都不写，下一次干净启动**仍然**会问——这正是"本次"该有的意思。判据也必须是**两条一起**：

- 只看"没有凭据"不行——凭据约两天过期，那会变成每次过期都拦一下；
- 只看"配置没记录"不行——已经登着号的人每次启动都被拦一下。

**退出账号不删任何文件。** 它是为了**换号**，不是为了清场，所以：

```
~/.skland/current        内容 = 当前账号 uid；**空文件 = 已退出账号**
~/.skland/cred_<uid>.json  每个登过的号一份，退出后原样留着
~/.skland/pending.json   登录在途的票据（拿到 hgToken 时 userId 还不知道）
```

`current` 的**三种状态**是这套设计的枢纽：非空 = 那个 uid；**空文件 = 已退出账号**；**文件不存在 = 旧单文件模式**，此时退回读 `cred.json` 的 `userId`。"空"与"不存在"必须分开——混成一种，老用户的凭据会在升级后凭空失效。

`pending.json` 的名字**故意不带 `cred_` 前缀**，否则 `known_accounts()` 会把它当成一个账号扫出来。它也不是账号数据：登录链写两次（第一次 `userId` 还是 `None`），兑现之后必须清掉，否则下次 `finish_login()` 会拿一个过期的 `hgToken` 去重试。

⚠ **`finish_login()` 必须 pending 优先**：先读 `load_cred()` 会在"切换账号的中途重新登录"时**静默用错账号的 hgToken**——报错都报不出来。

### 登录账号 uid ≠ 游戏 uid（**这一层最容易搞错**）

凭据里的 `userId` 是**通行证账号 id**；森空岛数据里的 `uid`（`opers_*.json` 顶层那个）是**游戏 uid**。名册按后者存。

两者长这样（**示例值，不是任何真实账号**）：

| | 形如 |
|---|---|
| 凭据 `userId` | `1000000000001`（13 位，通行证账号） |
| 游戏 `uid` | `10000001`（8 位，森空岛数据的身份） |
| 昵称 | `Doctor#0001` |

**它们不相等，而且离线推不出对应关系**——账号 id 在 `player_info` / `opers` / `roster` 三份数据里都查过，一个字符都没有。所以只能问森空岛一次再记住：

```
~/.skland/accounts.json     {"<通行证账号id>": {"gameUid": "...", "nickName": "...", "channelName": "..."}}
```

键是**通行证账号 id**（它才是凭据的身份），值是游戏 uid（它才是数据的身份）。放这个独立文件而不是塞回凭据里，是因为老机器上凭据还是单文件 `cred.json`——那是只读的老格式，不该回写。

写入点有两处，都必须是"**问到了才写**"，不许猜：`skland fetch`（它本来就要拿绑定列表）与 `python tools/skland.py whoami` / TUI 登录屏的 `U`（2026-09-18 之前挂在 `[0]` 准备屏）。`resolve_game_uid()` 只走 `binding_list` 这一跳，比拉全量玩家数据轻得多。

`U` 是**按键**而不是开机自动问：它是联网动作，悄悄在挂载时打一次接口既让人对着界面等，又会把没网时的失败糊进启动过程。

**一个实测的坑**：`binding_list` 在凭据过期时回的是泛泛的 `code 10000 请求异常`——**与签名写错同码**，看字面完全看不出是过期。所以 `resolve_game_uid()` 遇到失败会先用已缓存的 hgToken 补一次 `cred` 再重问一次（补完仍失败才抛**原来那个**错，免得"过期"被"补登录失败"顶掉）。hgToken 也过期就只能重扫，那不是这一步能修的。

### 名册取错账号是这一类里最坏的错

`data/skland/` 下这时可能同时存着好几个 `roster_<uid>.json`（退出账号不删文件）。原先 `load_roster()` 写的是「按文件 mtime 取最新的那份」——切换账号之后它会**显示错账号的名册，而且不报错**：界面看着完全正常，报出来的练度却是别人号的。现在改成**按 `skland.current_uid()` 取那一个 uid 的文件**，取不到就往下退到 MAA OperBox（降级）或干脆没有。

守卫在 `tools/check_tui.py` 第 [16] 节，自检里那份"别人的名册"**故意写得更新**，就是为了让"按 mtime 取"这种写法必然露馅。

### 已裁定（2026-09-18）：小窗口里装饰让路，内容优先

博士连着报了两件事——「主界面只看得见四行标题」与「登录账号那一栏没有名册/干员库那句」——**同一个成因**：内容排在 30 行以下，而他的终端大约 20 行，**值全掉在下沿之外**，只剩标签行看得见（`_proto/home_fold.py` 量到：改前 80x20 时名册那句在 y=20，而窗口只有 0–19）。随后他给了通用口径：**「做好页面排版，保证终端窗口小的时候也要让玩家看到所有内容」**。

一个 `.block` 的固定开销是 **6 行**（上下边框、上下内边距、上下外边距各 1），三块 18 行，加上顶栏、步骤条、底栏——**要 25 行才装得下**。所以让路的是装饰，分三层（基类 `RiosScreen`，阈值都是量出来的）：

| 层 | 条件 | 做什么 |
|---|---|---|
| **`.block { height: auto }`** | 总是 | **最底下那一层成因**：Textual 的 `Vertical` 默认 `height: 1fr`，三块把剩余空间**均分**，各自被撑高几行，中间凭空多出空行、内容被顶到窗口下沿之外。块要贴着内容长，多余的高度留在最下面 |
| `compact` | 窗口高 < 22 | `Screen.compact .block` 收掉块的边框、内边距、外边距（**每块省 4 行**），步骤条压到 1 行。**所有屏共用**，列表屏因此能把多出来的行让给表体 |
| `TINY_HEIGHT` | 窗口高 < 16 | 连**顶栏**也收掉（服务名与时钟是装饰；底栏留着——那里的按键是操作） |
| `_fit_extra(h)` | 各屏自定 | 主界面只在窗口矮于 **11 行**时才收标题块（`height: auto` 修好后，这一屏 11 行就装得下全部四行数据）；解算屏把头顶四行压成三行、再压成两行（关卡/人数缩一行、计数缩一行，**一行内容都不丢，丢的只是换行**） |

内容比屏幕长的三处（解算日志 `#log`、结果正文 `#result`、登录态 `#login-status`）改成**可滚动**（`overflow-y: auto`）：滚一下就能看全，而不是"被截断就没了"。

判据是「**不滚动**就要看得见」——Textual 的 `Screen` 默认 `overflow-y: auto`，所以"能滚到的内容"从程序角度看都够得着，但博士看到的是"只看得见四行标题"：**没人会在一个终端界面里先想到去滚动**。所以量的是可见区（widget 与所有祖先区域的交集），只有 widget **自己**可滚动才算例外。

逐屏（主界面 / 登录屏 / 选关：章 / 关卡列表 / 改目录 / 解算中 / 结果屏 / 关卡表空 / 弹窗，**九屏**）× 逐档（80x12 / 80x16 / 80x20 / 100x30 / 120x44）钉在 `tools/check_tui.py` 的 `check_small_window()` 里；结果屏那一档喂的是**一百行假正文**（量它是可滚动的排版，不是内容）；主界面那两栏另在 `check_welcome()` 里逐行量（**10 行**这一档也量，超出支持范围但同样不许有内容掉出去）。

量出来的支持下限：**80x12 起每一屏都全可见**（登录屏三块最多，是那一档的瓶颈）。

### 已裁定（2026-09-18）：U 与 O 都挪去登录屏

博士原话：「这一句加在登录账号界面，并且把主界面上的取账号uid按钮去掉，退出账号按钮移动到登陆界面」。

| 键 | 原来在哪 | 现在在哪 | 为什么 |
|---|---|---|---|
| `U` 取账号 uid | `[0]` 准备屏 | **只留登录屏的 `U`**（补全账号信息） | 主界面那个只补**当前**账号，登录屏那个一次补齐**本机每个**账号（`resolve_game_uid_for`）——同一件事不留两个按钮，逻辑也不留副本 |
| `O` 退出账号 | `[0]` 准备屏 | **登录屏** | 退出是为了换号，而换号本来就在登录屏上做（那里才有账号列表与「按 S 切回」的上下文）；那行「按 O 退出账号——凭据文件保留……」的说明跟着一起搬 |

另外把这一屏做成**逐栏兜底**：任何一栏的取数抛了，就在那一栏写下「这一栏取不到：<异常>」，绝不留空白。起因是博士报「主界面只看得见四行标题」——空白是最坏的结果，它分不清「没登录」「没有名册」还是「代码在这台机器上挂了」，而这一屏正是别人第一次跑起来看到的东西。判据在 `tools/check_tui.py` 的 `check_welcome()`（含「模拟抛错 → 那一栏必须写出原因」与「一栏坏了不连累另一栏」两条）。

**登录屏的「补全账号信息」（`U`）是做什么的**（博士问过）：它**联网**问一次森空岛，把本机每个账号的**游戏用户名与游戏 uid**记下来（`skland.resolve_game_uid_for` → `~/.skland/accounts.json`）。非有它不可的原因：凭据里的 `userId` 是**通行证账号 id**（13 位），名册却按**游戏 uid**（8 位）存文件，而账号 id 不出现在任何一份森空岛数据里——这个映射**离线推不出来**，只能问一次记住。没问过的号在列表里就显示「游戏用户名未知」，按 `U` 补上即可（一个号失败不影响别的号）。

### 回放屏为什么去掉

原方案里有过一个「逐帧观看战斗」的终端界面（把 `sim` 的 30fps 推演画在终端上，看谁站在哪、几秒开技能、哪一秒漏怪）。

**博士裁定去掉，理由一句话就够：玩家拿到 JSON 导入 MAA，那本身就是实机作战回放。** 终端里再演一遍是重复劳动，而且演不过实机。

**这一刀的价值超出「少做一个功能」**：

- 它是**全案唯一需要动 `battle/sim.py` 的地方**——`BattleSimulator.run()` 是一次跑到结束、中间状态不落地的（`sim.py:913`），要做逐帧就得改它；而那个循环是**专门就地展开优化过的**（纯 Python 1.18×，见 README「战斗循环的就地展开」）。
- 砍掉之后，**`sim.py` 一行都不用碰**，那条热路径与全部三关基线（1-7 / SR-6 / SR-EX-8）保持原样，没有性能回归的风险。
- 于是全案需要动核心代码的地方**只剩一处**：给 `search.py` 加进度钩子（第六节）。

**由此得到一条可复用的判据**：界面层的功能若与下游工具（这里是 MAA）已经做的事重复，就不该在本项目里再做一遍——本项目该交付的是**作业本身**，不是它的演示。

索敌 → 位移 → 技能/天赋/模组 → 波次），每搬一块就跑一次对拍；全绿之后再接进搜索。

**博士 2026-09-18 对范围的裁定**：「先做一个最小版本，测试可行的话就完成重构」。
所以第一步不是全量移植，而是**常规关卡（无装置、无特殊机制）的最小闭环** + 对拍台：
最小版本在 1-7 这类关卡上与 Python 版判决一致，就继续往全量做；不是，就先改方案。

**已落地的第一步**（提交见 `rios-sim/`）：Go 骨架 + stdio 的 JSON 行协议 + `ping`
（协议版本核对）+ 出错一律 `ok:false`（**绝不返回假判决**，否则对拍台失效）。
门口自检 `tools/check_simgo.py`（本机没装 Go 时跳过，不拦别人）。

**已落地的第二步（2026-09-18）：最小版本 + 对拍台，24 例全绿。**

* **最小版本**（`rios-sim/sim.go`）实现了常规关卡的完整主循环，帧内顺序逐条对上
  原版：费用回复 → 部署（含费用门与再部署冷却）→ 出怪 → 推进（分段计划）→ 阻挡
  → 我方出手 → 敌方出手（含 `enemy_windup` 与连击分段结算）→ 结算（击杀回费、漏怪扣命）。
  敌人路线以**分段折线**送过去（Python 侧用 `sim._spawn()` 现成的实例），所以寻路
  不会成为第二份实现。
* **边界靠拒跑守住**：用到技能（含自动开）/装置/召唤/撤退/位移/控制/持续伤害/场地机制
  时，Python 侧把原因写进 `spec.unsupported`，Go 侧**拒跑**。宁可让对拍台看见"这一局
  还不支持"，也不能拿缺了机制的结果去"对齐"——那种对齐会把 bug 固化成基线。
  两个口子（`allow_devices` / `allow_skills`）**必须带证据**才能开：装置要"摘掉重跑
  结果一字不变"，技能要"原版这一趟一次都没开"。
* **对拍结果**（`_proto/simgo_parity.py`，12 关 × 2 阵容 = 24 例）：`won` / 击杀 /
  漏怪 / 部署 / 阵亡 / 出怪数 / 超时 **逐位相等**，耗时与总伤害按 1e-6 相对容忍相等，
  漏怪明细逐笔相等。单场 Go **0.5–2.1ms** vs 原版 **60–320ms**，约 **100×**。
* **门口自检**已含 3 例对拍（`tools/check_simgo.py`，16 项全绿，约 3 秒）。

**端到端的账**（`python tools/simgo_cost.py`，量的是"一场战斗"的两段成本）：

| 关卡 | 出怪 | 原版跑一场 | 建规格（Python） | Go 跑一场（含进程往返） | 合计 | 加速 |
|---|---|---|---|---|---|---|
| 1-7 | 41 | 1150ms（首场含预热，常态约 120ms） | 1.4ms | 3.5ms | 5.0ms | 232× |
| 2-1 | 50 | 240ms | 2.0ms | 5.7ms | 7.7ms | 31× |

两条结论：

1. **序列化的成本可以忽略**（1–2ms），瓶颈不在这儿——所以不必为"缓存出怪段"做额外设计；
2. **单场 5–8ms vs 原版 75–250ms**，一次 HS-EX-4 量级的解算（约 2880 场）预计从
   **214 秒降到 20 秒上下**——这与博士要的"一个量级"对得上。

⚠️ **但那两个最需要提速的关卡现在跑不了**：`SR-6` 拒跑于「全场总攻击装置」，`HS-EX-4`
拒跑于「场地机制（田地/病害值）」——它们恰好是基线关与 214 秒那一关。所以接下来的
移植顺序不是随便排的：**技能 → 场地机制（田地/病害值）→ 全场总攻击装置**，前两项
是打通 HS-EX-4 的必经之路。

**关卡特有机制落在哪一层（博士 2026-09-18 裁定）**：「场地机制等关卡特有机制单独拿出来，
不要放在模拟器里」，补充「做成 go 侧的**独立层**，同时把**每个活动的机制分开**，**按需取用**」。
所以后两样落进 `rios-sim/mech/`（**一个活动一份文件**，`init()` 注册自己），主循环只留
"时间怎么走、谁打到谁、死了没有" 与三个固定位置的帧回调，不出现任何逐关特判。
机制由 `spec.mechanisms` 点名、按需装载；点了一个本二进制里没有的名字 → **拒跑**
（与 `unsupported` 同源：少挂一个机制与"本来没这机制"在判决上分不开）。
这一层已经落地（README 有完整口径），**当前是空层**，对判决的影响为零——
24 例全量对拍与 `check_simgo.py` 全绿即证据。

**技能那一层怎么切的（2026-09-18 落地）**：技能其实是**两件**事，归属不一样。

* **数值**（开着的时候攻击力/攻速/伤害类型/目标数/倍率/连段是多少）——由 Python 侧
  用**原版自己的读数函数**算好，**两套**一起送过去：`OperatorSpec` 顶层那套是"没开技能"，
  `active` 那套是"技能期间"。做法是临时把 `skill_active`/`effects_override`/
  `skill_attack_type` 摆成开启态、读完立刻 `try/finally` 还原。Go 一个数都不算。
  为什么不逐项送"改了哪几项"：那等于在 Go 侧把效果模型抄第二遍，而效果模型正是全仓
  最容易漂的一层（`SkillEffects` 六十来个字段）。
* **状态机**（攒技力、够不够开、开多久、弹药打光、被动常驻）——**只能在 Go 跑**：
  "够不够开"取决于战斗中发生的事（出手回复、受击回复、手动请求落在哪一帧），事前算不出来。
  判据逐条照抄 `sim._skill_tick`，包括两处看起来不一致、但**必须照抄**的技力上限
  （未开启攒技力是 `sp_cost × max(1, max_charge)`，出手回复却封顶在 `sp_cost`）。

只收一个**白名单**：逐字段拿 `dataclasses.fields(SkillEffects)` 与默认值比，
白名单外一律拒跑——**新字段自动落进"不支持"**（黑名单会静默按旧口径跑）。
覆盖面（`_proto/skill_coverage.py`，判据与实现同源）：全库 1005 条技能里
**257 条（25.6%）**在子集内，攻速/攻击力/防御/真伤/倍率/多段/多目标/瞬发/无限/
弹药/被动/自动触发/整场一次/回费/攻击回复/受击回复**每根轴都有例**。
对拍（`_proto/skill_parity.py`，20 例按轴铺开）**全部逐位一致**，
其中"开了 0 次技"的用例会**自己报出来**（判决一致但该轴没被验证＝假绿）。

**这一层咬人的三个坑**（都已留守卫）：

1. **`null` 到 Go 就是 `0`**：Python 送 `"final_hit_scale": null`，Go 的 `float64` 收到 0，
   而"有没有末击加倍"当时是按 `!math.IsNaN()` 判的——于是单发攻击的最后一击（也就是
   唯一那一击）倍率被改成 0，**打不死人但不报错**。修法：可选数值 Go 侧一律用**指针**
   （判 `nil`），Python 侧**不许发 `null`**（没有就整个键不出现），
   并加了一条把整份规格扫一遍、见到 `None` 就红的检查。
2. **弹药类的"无限"**：原版判的是 `effective_duration is None`（三种来路：弹药、
   描述写「持续时间无限」、durationType=INFINITE），我当时读的是 `sk.infinite`
   ——弹药类会被读成 **0 秒瞬发**，开启那一帧就结束。守卫：库里查一条 AMMO 技能，
   断言必须报成 `infinite=True 且 ammo>0`，并配一条反向守卫（有限时长的技能不许报无限）。
3. **`combo_hits` 的"没有"是 1 不是 0**：按真值判会把**每一位没有连击的干员**
   全挡在门外（实测阿米娅就中招）。同类：`Deployment.skill` 的默认值 0 会在部署时
   把干员身上已绑的技能**清掉**（`_attach_skill` 的行为）——所以对拍用例必须走
   `Deployment.skill`，而"生成规格"那一步也得照做同一个分支，否则规格里带着技能、
   那一趟却没有。

**下一步**：把"判决一致但一次没开技"的那三根轴（攻击回复/受击回复/弹药）用
**能覆盖路线的落点**真正跑起来（落点目前是按地图格序随手取的，落错位置就等于
没验），再按 场地机制（田地/病害值）→ 全场总攻击装置 的顺序补机制层；
最后在 `search.py` 里加适配层（**默认仍走原版**），拿 HS-EX-4 量一次端到端。
