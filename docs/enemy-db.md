# 敌人库：PRTS 敌人页 → `data/enemydb.sqlite`

`python -m ak_tactic enemydb build` 会把 **prts.wiki 的『分类:敌人』**（约 1800 页）
解析进一个**独立的库文件** `data/enemydb.sqlite`，里面四张表：
`enemy` / `enemy_level` / `enemy_resist` / `enemy_skill`。

## 与干员库是两回事

敌人的库和干员的库**不共用文件、不共用结构版本、不互相引用**：

| | 干员库 | 敌人库 |
|---|---|---|
| 文件 | `data/akdb.sqlite` | `data/enemydb.sqlite` |
| 来源 | 游戏本体 gamedata 的 `excel/` | prts.wiki 的「分类:敌人」 |
| 更新节奏 | 跟着游戏版本 | 跟着站内编辑 |
| 主键 | `char_id`（`char_002_amiya`） | PRTS 页名（`“死志的凝结”`） |
| 数值口径 | 只存**关键帧原文**，面板另算 | 存**算好继承的逐档数值** |
| 建库 | `python -m ak_tactic db build` | `python -m ak_tactic enemydb build` |
| 查询 | `python -m ak_tactic db …` | `python -m ak_tactic enemydb …` |
| 自检 | `tools/check_db.py` | `tools/check_enemy_db.py` |

放一个文件里最坏的地方不是乱，是**数值口径正好相反**：干员那边存原文、算在代码里，
敌人这边没得选（PRTS 页面里没有"显式/继承"标志位）只能建库时算好。
同一个文件里两种口径并存，读的人迟早按错的那套读。

查询：

```powershell
python -m ak_tactic enemydb find 死志          # 找敌人（按页名/名字/编号）
python -m ak_tactic enemydb find --grade 领袖    # 只列领袖
python -m ak_tactic enemydb show 源石虫          # 一个敌人的完整战斗数据
python -m ak_tactic enemydb show "“死志的凝结”"   # 页名带全角引号，注意引号
python -m ak_tactic enemydb show 挥铳圣像 --json  # 原样 JSON
python -m ak_tactic enemydb sql "select page,name,grade from enemy where grade='领袖' limit 5"
python -m ak_tactic enemydb info                 # 版本戳与行数
```

> 别和 `python -m ak_tactic enemy 源石虫` 搞混：那条是**实时**从 gamedata 取一个
> 敌人的图鉴与数值（走 `EnemyLibrary`，不碰这个库）。

## 一、为什么是 PRTS，而不是游戏本体

敌人数据其实有两个来源，都能拿到：

| | 游戏本体 gamedata（`levels/enemydata/enemy_database.json`） | PRTS 敌人页 |
|---|---|---|
| 逐档数值 | 有（原始 Unity 结构，`m_defined` 合并） | 有（模板参数，SMW 继承） |
| 天赋黑板（P3R 相性 / 倒地阈值 / 重生参数） | 有（`talentBlackboard`） | **有**，以 HTML 注释形式原样带出 |
| 图鉴文本（描述 / 能力 / 编号 / 种类 / 登场活动） | 只有名字与描述，散在两处 | 有，且是站内编辑整理过的 |
| 敌方技能（首次冷却 / 周期冷却 / 技力 / 效果） | 有原始 `skills`，但无中文名 | 有中文名与效果正文 |
| 抗性 | 11 项布尔位 | 十余项「有 / 无」+ 损伤抵抗 / 元素抗性 |

也就是说 PRTS 把**图鉴 + 数值 + 抗性 + 技能 + 黑板**放在同一个地方，一个源就够，
不必再拿 gamedata 的敌人库去补。**但两者是同源的**——PRTS 的数值本来就是从游戏里
整理出来的，所以这不是"另一个数据"，而是"同数据的另一种组织方式"。

正因为同源，`tools/check_enemy_db.py` 才会拿**游戏本体**去对账：两边一起错的概率，
远低于解析器单独错的概率。当前 9 个锚点（SR-EX-8 的 8 个敌人 + 源石虫）
**生命 / 攻击 / 防御 / 法抗 / 重量 / 档数** 逐项一致。

## 二、取数：一次抓 1804 页

* 页名来自 `分类:敌人`（`categorymembers`，500 条一页，4 次请求）。
* 正文用 `action=query&prop=revisions&rvslots=main&titles=A|B|…` **批量取**，
  MediaWiki 一次最多 50 个标题（机器人 500），故 1804 页只要 **37 次请求**。
  单批实测 1.4 s / 67 KB。
* 每次请求都被 `PrtsClient` 的磁盘缓存（`data/cache/prts/`，TTL 7 天）按 URL 收下，
  **重跑不重复打网**：首次建库 50.8 s，之后基本只剩解析时间。
* 限速仍是 1.2 s/请求（PRTS 的 WAF 按来源 IP 计），所以首次那 37 次请求要
  一分多钟。

## 三、表结构

### `enemy`（图鉴级，1 行/页）

`page`（**主键**）· `prts_id`（模板 `id`）· `name` · `display_name` · `index_code`
（图鉴编号如 `B1` / `SD13`）· `grade`（普通 / 精英 / 领袖）· `category`（种类）·
`damage_type` · `attack_way` · `move_way` · `camp` · `description` · `ability` ·
`ability_fixed` · `ability_errata` · `debut_event` · `is_irregular` ·
`has_handbook` · `level_count` · `raw_wikitext`

页名做主键，而不是名字：敌人的中文名会撞车（「“阿米娅”」与「阿米娅」是两回事）。

**`ability` 与 `ability_fixed` 是两份不同的文本，不是"清洗前后"**：前者是
**游戏内原文**（模板 `能力`），后者是**站方勘误后**的读法（模板 `能力修正`，
展开 `修正lite` 标记）。114 页有勘误，`ability_errata` 留原始标记以便追溯。
详见第四节末尾。

### `enemy_level`（逐档，1 行/档）

数值：`hp` `atk` `defense` `res` `move_speed` `attack_speed` `base_attack_time`
`hp_recovery` `sp_recovery` `weight` `range_radius` `target_value`
`damage_resistance` `element_resistance` `taunt_level`

其中两项**语义容易读错**，单列出来（原表见第四节末）：

| 列 | 模板参数 | 语义 |
|---|---|---|
| `move_speed` | `移动速度` | 格/秒还要乘关卡系数，`格/秒 = move_speed × 关卡 moveMultiplier × speed_scale` |
| `target_value` | **`数量`** | **漏掉它扣几点关卡生命**（模板里被 `#vardefine` 成了「目标价值」），不是"场上有几个" |
| `range_radius` | `攻击范围半径` | **空 = 近战（半径 0）**，不是"没有数据" |

文本与结构：`name` `grade` `category` `description` `description_fixed`
`attack_way` `move_way` `talent`

技力槽：`init_sp` `max_sp` `sp_recovery_type` `sp_recovery_value`

追溯用：`params`（生效参数全量）· `explicit_params`（本档**显式**写出的）·
`hidden_params`（注释掉的）· `blackboard`（拍平的黑板）· `blackboard_raw`

### `enemy_resist`

`page` `level` `name`（如 `眩晕抗性`）`value`（原文，`有` / `无` / `免疫`）
`is_immune` · `source` · `is_effective`

以 `抗性` 结尾的参数**一律收进来**，不写死名单——PRTS 模板加一项，这里自动跟上。

**`source` 两种取值的语义不同，不能混排**：

| source | 来源 | 例 |
|---|---|---|
| `字段` | 标准 `眩晕抗性=有` 那一批 | `沉默抗性=有` |
| `覆写` | `抗性覆写={{异常效果|眩晕|免疫}}` | 同上，但写法不同 |

**`覆写` 压过同名的 `字段`**，主键并入 `source` 就是为了让两者并存而不互相顶掉。
`is_effective` 已经把胜负算好——要"这个敌人的真实抗性"就查 `is_effective=1`，
别不过滤直接取全部。API 里对应 `effective_resists()`。

### `enemy_skill`

`page` `level` `slot` `name` · `init_cooldown`（**首次**就绪冷却）·
`cooldown`（**之后每次**就绪冷却）· `sp_cost`（技力消耗）· `kind` · `effect`

## 四、解析的四个坑

### 1. 高档位只写被改写的字段，其余继承

`级别1` 常常只有 `index` 与 `最大生命值` 两行。PRTS 模板里每个字段都写成
`{{{字段|{{#ask:[[<页名>#LEVEL<index-1>]]|?字段}}}}}`，即**向上一档取**，
由 SMW 在渲染时完成。

本库在建库时就把继承算好（落在列里），同时把**本档显式写出的参数**留在
`explicit_params` 里，用来分辨"这一档真的改了没有"。这与干员那半边"只存关键帧
原文"的做法**不同**——PRTS 页面里没有"显式 / 继承"的标志位，只有"写了 / 没写"。

### 2. 黑板藏在 HTML 注释里，且解析参数前必须先剥注释

```wikitext
|天赋=…<!--[
    { "key": "Mode_A.PHYSICAL", "value": 0.0 },
    …
]-->
}}
```

黑板（P3R 相性、倒地阈值 `TotalAttack.weak_max`、重生参数 `Reborn.*`）
就是这样嵌进来的。**必须先把注释抽出来，再剥掉注释解析参数**：
注释里那串 JSON 满是花括号，留着会把模板配对数错开。

### 3. 注释掉的参数是"页面上不显示"的，但往往是真的

```wikitext
|index=1<!--
|名称=死志暗影-->
```

PRTS 页面上这一档仍显示「“死志的凝结”」（因为 `名称` 被注释掉了，走了继承），
而**游戏数据里的名字是「死志暗影」**。

本库两者都留：生效参数进列，注释参数进 `hidden_params`。谁也不替谁下判断。
全库 2108 档里只有这 1 档有这个情形，但它是"注释必须单独处理"这件事的活证据，
`check_enemy_db.py` 专门钉了它。

### 4. `技能N初始` 是**冷却**，不是初始技力

模板表头写得很清楚：

* `play-circle` = `技能N初始` = 该技能**第一次就绪**所需的冷却时间（秒）
* `circle-slice-5` = `技能N消耗` = **第一次释放之后、下次就绪**所需的冷却时间
* `技能N技力` = 技力消耗（为 0 时页面上显示 `/`）

按"初始技力 / 消耗"去理解会整体读反。另有三项 `初始技力` / `技力上限` /
`技力槽回复类型` / `技力回复速度` 是**敌人自己的技力槽**，与技能无关，落在
`init_sp` / `max_sp` / `sp_recovery_type` / `sp_recovery_value`。

### 附：两个语义容易读错的字段

* **`数量` 就是「目标价值」**。模板里 `{{#vardefine:目标价值|{{{数量|…}}}}}`，
  语义是"该敌人走到路径终点退场时扣几点关卡生命"，落到 `target_value`。
  不是"场上有几个"。
* **`攻击范围半径` 为空表示近战（半径 0）**，不是"没有数据"。存成 NULL，
  别在查询里把它当缺失值过滤掉。

## 五、字段审计：上游写了、解析器却没认的那些（2026-09-16）

白名单式解析的代价是**静默少数据**：上游加个参数、或者某页换个写法，
不会报错、行数照旧，只有拿模板逐字段点才算得出来。这件事已固化成工具：

```
python tools/enemy_field_audit.py          # 全量（走磁盘缓存，不联网）
python tools/enemy_field_audit.py -v       # 连已入库的也逐条列出
```

输出是**总账**：每份模板的每个参数归到「入库（去了哪张表）／认识但丢弃／
非战斗数据／未入库」四类之一，退出码非 0 即存在未入库的字段。

第一次跑（1804 页）跑出 8 种没去处的参数，其中 **4 处是真漏**：

| 参数 | 次数 | 问题 | 处置 |
|---|---|---|---|
| `抗性覆写` | 2 档 | 用 `{{异常效果|眩晕|免疫}}` 记法，**压过**同档的 `*抗性` 字段 | 解析进 `enemy_resist`，`source='覆写'`，`is_effective` 算好胜负 |
| `技力初始` | 2 档 | `初始技力` 的**词序颠倒**写法 | 两种词序都收 |
| `能力修正` | 114 页 | 站方勘误，与 `能力` 是**两份文本** | 新增 `ability_fixed` / `ability_errata` |
| 档位 `描述` 的内联 `修正lite` | 6 档 | 勘误标记混在正文里 | 新增 `description_fixed` |

### 1. `抗性覆写` 压过标准字段——照字段读会给错答案

「蔓德拉」是活例：她的 `眩晕抗性` / `沉默抗性` / `冻结抗性` 等标准字段**全写「无」**，
而 `抗性覆写` 写着七项免疫。只读字段会把她记成"什么都不免疫"。

它还能表达标准字段表里**根本没有的项**（`{{异常效果|失衡免疫}}`、
`{{异常效果|强制缴械|免疫}}`），这也是它存在的意义。

处置：两类都入库、不丢数据，用 `source` + `is_effective` 标明谁说了算。
要真实抗性就查 `is_effective=1`（API：`effective_resists()`）。

### 2. `能力` 是**游戏内原文**，不是"过期文本"

`{{修正lite|修正后内容|原文=游戏内原文|原因=N}}` 的模板说明写得很直白：

> 此处游戏内原文是X，因<原因>，我们对其进行了修正。

所以 **`能力` 是游戏原文、`能力修正` 是站方勘误**，两者都不是"清洗前后"的关系。
原因码：1 笔误 / 2 日服变更 / 3 用语未统一 / 4 误译 / 5 漏译 /
**6 描述与游戏实际表现不符合** / 7 游戏文本存在疏漏 / 8 表述歧义。

实测 114 页有勘误，**179 处新文本不在 `能力` 里、77 处旧文本在 `能力` 里**。
最刺眼的是「大总统」汉科：原文「并使其中所有单位的隐匿和迷彩失效」，
勘误插入「不会」→「并**不会**使……」——**语义整个反转**。

对模拟器而言勘误文本更贴近实际机制，所以两份都留：`ability` 存原文、
`ability_fixed` 存勘误后文本，谁也不覆盖谁。

### 3. 空串的语义是**继承**，不是置空

模板把每个字段写成 `{{{字段|{{#ask:…}}}}}`，而 MediaWiki 的 `{{{x|默认}}}`
在 x **为空**时同样采用默认值——所以 `|技力初始=` 的意思是"继承上一档"。

原实现 `{**merged, **carry}` 让空串顶掉了继承值，实测 **4 个页面 8 处**静默少数据，
且都咬在战斗字段上：

* 「杜卡雷，"君主之红"」档 2 的 `攻击范围半径` 2.2 被抹成 NULL → **读出来就是近战半径 0**；
* 「反巫术变位炸弹」档 1 整个技力槽与技能名「爆炸」消失；
* 「碎铳之簧」两档的 `描述`、「炎佑」档 1 的技能名。

空值仍原样留在 `explicit_params` 里，追溯得到"这一档确实写了空"。

### 4. 有意不收的：档案评级字母块

个别页面（「“Mechanist”，机械之心」「结构性原理(敌方)」）把敌方档案的
**S/A/B/C/D/E 评级**写在 `common2` 里：`|攻击力=A`、`|移动速度=D`、`|法术抗性=B+`。
麻烦在于**参数名与逐档数值字段完全同名**，判据必须带语境——`common2` 里这些是
评级（不收），`levelcontent` 里是真数值（照收）。图鉴级本来也不参与数值解析，
忽略它们不丢任何战斗数据。

另有 4 类确认非战斗数据、有意不收：`相关敌人`（站内互链）、`无头像`（立绘标记）、
`特殊分类`（主题标签如「球员」）、`位置`（展示用）。

### 5. 复核：「死志的凝结」三层对读

改完拿 BOSS 页做了原文 / 解析 / 库三层对读，全部吻合，并坐实两件事：

* **黑板是逐档不同的**：`Mode_A.attack@power_atk_scale` 档 0 是 2.5、档 1 是 **3.5**；
  `Mode_B.move_speed` 从 2.0 变 1.0。此前只记了档 0 的值。gamedata 那一侧读的是
  **档 1**（`enemyDbRefs` 里唯一非 0 的），26 个黑板键与 prts 逐键一致、零差异。
* **`眩晕抗性=无` 不代表不免疫眩晕**：该页 `*抗性` 字段写「无」，而天赋正文写着
  「持有{{异常效果|晕眩|免疫}}（【倒地】期间无效）」。**免疫可以写在正文里**，
  字段不是唯一真相源——这正是要把它编译成公式项的理由（见第四件事）。

## 七、已知未尽事项

1. **「同构碎片」是唯一零档的敌人**（非常规、无图鉴，页面 299 字，本来就没有
   `levelcontent` 模板）。不代它编一档，`check_enemy_db` 断的是"有图鉴却零档"为零。
2. **16 个敌人没有地位、10 个没有行动方式、22 个没有攻击方式**——PRTS 页面上
   就是空的（多是关卡脚本生成物，如「落石」「喷口」「结晶」）。按空存，不猜。
3. **PRTS 的敌人页是"通常数据"**，页面自己注明：具体到某一关可能被关卡页的
   「敌方情报」覆写。本库收的是**页面级通常数据**，不含关卡级覆写。
4. **页数与游戏本体敌人 id 数不等**（1804 页 vs 2151 个 id）：PRTS 按"敌人条目"
   组织，同一个敌人在不同关卡的不同档位不重复建页；也会出现有 id 无页
   （纯脚本生成）与有页无 id（编辑整理的条目）。
5. **`raw_wikitext` 存了整页原文**（含被注释的参数），是这一层唯一的兜底；
   `enemydb show` 的详情输出不带它（太大），要看得走
   `enemydb sql "select raw_wikitext from enemy where page='源石虫'"`。
6. **本库与 `python -m ak_tactic enemy <名字>` 是两码事**：后者是**实时**从
   gamedata 的 `enemy_database.json` 取一个敌人的图鉴与数值（走 `EnemyLibrary`，
   不碰这个库），适合临时看一眼；前者才是可 SQL 的全量库。两者的数值在
   9 个锚点上已逐项对过账（见第八节），但**字段口径不同**——那条实时路径的
   `EnemyStats` 字段叫 `max_hp` / `magic_resistance` / `life_point_reduce`，
   本库叫 `hp` / `res` / `target_value`。

## 八、验证

```powershell
python -m ak_tactic enemydb build            # 重建（首次约 51 s，之后走缓存约 5 s）
python tools/check_enemy_db.py               # 60 项
python tools/enemy_field_audit.py            # 字段总账，退出码非 0 即存在未入库字段
python tools/check_db.py                     # 55 项（干员库，另一个文件）
```

`check_enemy_db.py` 分六类：**出处与自洽**（版本、来源、行数、`level_count`
与逐档行数、孤儿行）、**覆盖**（有图鉴比例、生命值非空、黑板与天赋的档位数）、
**跨源对账**（9 个锚点对游戏本体，逐项比较生命/攻击/防御/法抗/重量与档数）、
**解析口径守卫**（注释参数、继承、冷却语义、形态相性、免疫项数，每一条都对应
一个真踩过的坑）、**查询入口冒烟**、**字段审计**（`抗性覆写`/`技力初始`/
空串继承/勘误两份文本，见第五节）。

`enemy_field_audit.py` 与它是**互补的**：检查脚本断的是"已知的口径别回退"，
审计脚本找的是"还不知道自己漏了什么"——上游加字段、某页换写法，只有后者能发现。
