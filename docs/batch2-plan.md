### ⚠️ 一个我自己踩过的坑，写在这里防复发

上面这份清单**第一版是错的**：我当时写"机械师/圣聆初雪/安洁莉娜三处 token 属性
全为 0、phase 只有 -1，是标记"。**错在我取数的姿势，不在数据。**

`operator_attr` 有 `kind` 两态（`docs/operator-db.md` 有记）：

| kind | 行数 | phase | 含义 |
|---|---|---|---|
| `phase` | 4304 | 0..2 | **等级帧**——真实属性 |
| `trust` | 997 | **恒为 -1** | **信赖帧**——值是"信赖 0%/50%/100% 时的**增量**"，不是绝对属性 |

`-1` 是 `db/build.py` 里 `_phase_index` **故意**给的哨兵（注释：「取不到就给 -1，
宁可显眼，别静默变成 0」）。而 `-1` 在 `ORDER BY phase` 里**排在最前**——于是

```sql
SELECT hp, atk FROM operator_attr WHERE char_id=? ORDER BY phase LIMIT 1   -- 错的
SELECT ... WHERE char_id=? AND kind='phase' AND phase=0                    -- 对的
```

读到的是信赖增量（0% 那档恰好是 `hp=0.0 atk=0.0`），被当成了"单位属性"。

这个坑**不止影响召唤物**：997 行信赖帧分布在约 499 名干员上，任何漏过滤的查询
都会中招。`docs/roadmap.md` 里早就记过同族的一条（「`kind='trust'` 的行 cost 是 0，
不过滤会把所有人算成 0 费」）。**同类错误在本项目已发生第二次，写 SQL 时先想
`kind`。**

在全套自检上花的时间要留给真正的建模。改动累积到要**上传 GitHub 时**再跑一次
全套自检与三条基线。改动 `battle/` 主循环或伤害结算这类会波及基线的部位时，
例外——那类改动当场就要跑。
