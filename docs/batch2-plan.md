## 判据

**「已建模」= `ak_tactic/battle/` 里有对应结算。** 只在 `formula.py` 里编出公式项、
战斗层没人消费，**不算数**——闪避此前就是这样整条链路静默失效的（见 `roadmap.md`）。

批次二的六个大件：**召唤物 / 屏障·护盾 / 状态机 / 弹药 / 位移 / 随机**。

## 一句话结论

**先做召唤物。** 理由不是它最简单，恰恰相反——它牵扯最广，而且是练度第一的
**电弧**的整套 kit：电弧技1/2/3 各换一种塔，塔本身就是召唤物。她现在的战斗行为
等于零。数据层已经查清、够用（见下节），所以这是**最该先做也做得动**的一件。

### ⚠️ 一个我自己踩过的坑，写在这里防复发

上面这份清单**第一版是错的**：我当时写"机械师/圣聆初雪/安洁莉娜三处 token 属性
全为 0、phase 只有 -1，是标记"。**错在我取数的姿势，不在数据。**

`operator_attr` 有 `kind` 两态（`docs/operator-db.md` 有记）：

| kind | 行数 | phase | 含义 |
|---|---|---|---|
| `phase` | 4304 | 0..2 | **等级帧**——真实属性 |
| `trust` | 997 | **恒为 -1** | **信赖帧**——值是"信赖 0%/50%/100% 时的**增量**"，不是绝对属性 |

`-1` 是 `db/build.py` 里 `_phase_index` **故意**给的哨兵（注释：「取不到就给 -1，
宁可显眼，别静默变成 0」）。而 `-1` 在 `ORDER BY phase` 里**排在最前**——于是

```sql
SELECT hp, atk FROM operator_attr WHERE char_id=? ORDER BY phase LIMIT 1   -- 错的
SELECT ... WHERE char_id=? AND kind='phase' AND phase=0                    -- 对的
```

读到的是信赖增量（0% 那档恰好是 `hp=0.0 atk=0.0`），被当成了"单位属性"。

这个坑**不止影响召唤物**：997 行信赖帧分布在约 499 名干员上，任何漏过滤的查询
都会中招。`docs/roadmap.md` 里早就记过同族的一条（「`kind='trust'` 的行 cost 是 0，
不过滤会把所有人算成 0 费」）。**同类错误在本项目已发生第二次，写 SQL 时先想
`kind`。**

- [x] **位移·接线**（2026-09-18 落地，守卫 `check_battle` 第 `[26]` 节）：
  **落地方式**：`EnemyUnit.displaced`——一个与 `progress` **并列**的坐标，`None`
  表示在路线上。被推时设上它、`progress` 原地不动；之后每帧朝「当前进度对应的
  那一点」走回去，走到了就清掉、恢复按 `progress` 推进。**没有改掉 `progress`
  这套表示**，所以漏怪判定（只看 `progress`）与全部 `.position` 的消费者都不动。

  **两个坑，都是接线时才现出来的**：

  1. **阻挡是 latch 的。** `advance` 开头就是「被阻挡就不动」，而
     `_update_blocking` 只在**阻挡者阵亡**时清 `blocked_by`。所以推动时必须
     **顺手解除阻挡**，否则被推开的敌人会永远顶着 `blocked_by` 站在路线外——
     推动被**静默吃掉**，没有任何报错。
  2. **`EnemyUnit.cell` 是方法不是属性**（`Device.cell` 才是属性，两个类同名不同物）。
     第一版写成 `e.cell not in cells`，拿到的是"绑定方法对象"，永远不在集合里，
     于是推击循环**每次 `continue`、一个敌人都推不动**。库里正确的写法是
     `e.cell()`。这条是守卫抓出来的——**又一处"看起来实现了"**。

  **触发方式**：技能开启瞬间一次性推动（描述写"立即……并推动"），挂在
  `_activate` 上与 `_spawn_qi` 并列。方向取 `op.facing`（部署方向），
  距离查 `displace.push_distance(力度等级, 重量)`。力度只认 `force` 键，
  它是**力度等级**（"中等力度" = 中力 = 1），不是距离。

  **未做**：位移的**弹道时间**（`push_time`）没接——现在是瞬时的；拉动（`attract`）
  没接，圣聆初雪技3 的「诱导」是另一套机制；`force` 目前**没有**进
  `SkillEffects` 的分类表，是直接从 `blackboard` 读的。

  **位置是从路线进度算出来的**
  （`unit.py:828` `point_at(route, progress)`），所以"把敌人推出路线"目前
  **没有表示**——只改坐标会被下一帧的路线重算抹掉。要真接线得先给敌人加
  "偏离路线的位移"这一层表示（或改成 2D 位置 + 重新寻路）。这是**架构改动**，
  不是补一个字段，故与规则层分开做。详见 `docs/uncertainties.md` 第十节。
  - 推动：圣聆初雪技1（`force 1.0` = 中力，方向力、**特效类**，沿部署方向）。
  - 诱导：技3（「诱导攻击范围内所有敌人至自身周围的可达地面」）——与推动不同源。
  - 自身位移：赤刃技2「斩击 + 移动到目标位置」——第三种，动的是干员不是敌人。
  - 数据已备：gamedata 的 `enemy.weight`（= `massLevel`，`gamedata/enemy.py:507`）。
    **注意敌人库里没有这个字段**（只有 gamedata 有），别去 enemydb 找。
- [x] **弹药**（2026-09-18）：`ammo_left` 的**数据层与行为层都是通的**——
  开启时按 `effects.ammo` 装填、每次攻击扣一发、扣到 0 就结束（`sim.py` 的
  `_activate` / `_deactivate` / 攻击处），守卫在 `check_battle` 第 `[24]` 节。

  **但这一查查出一个真 bug**：提丰技3「永恒狩猎」是弹药技，`effects.ammo`
  却是 `None`，`int(None or 0) == 0`，于是**技能一开启就结束**。

  根因是**技能槽标记的两种写法**：`attack@atk_scale_s2` 把槽号写在**尾巴**
  （`_SUFFIX_RE` 管得着），而 `attack@s3_atk_scale` 把槽号**夹在 @ 后面**——
  原先的四级降级匹配**全都够不着**。提丰技3 整块黑板都是后一种写法，于是
  `atk_scale` / `stun` / `trigger_time` **四个键一起落进 `other`**：不只是
  弹药没了，攻击倍率和晕眩也一起丢了。

  修法是补一条中缀剥离 `_INFIX_RE = re.compile(r"@s\d+_")`。影响面已核验：
  全库这种形态只有 **6 个技能、11 个键**，其中另 5 个（`crosly`技3、
  `quartz`技2、`reed2`技3、`sankta`系…）也一并修好。

  **如实记下没做的**：`attack@s3_max_hit_num`（"共造成 5 次伤害"）**仍归不了
  类**——它是不是 `times` 没有旁证，不猜，守卫里钉着它还在 `other` 里。

  **顺带一条教训**：断言要跟被断言的配置一致。第一版守卫按 M3 断言"弹药 10"，
  而 `Deployment` 不指定专精时走 M0（8 发），于是**明明修好了却报红**。
- [x] **随机·审计**（2026-09-18）：十位干员的技能黑板里**恰好 3 个**带概率键，
  已逐条分类（审计守卫在 `check_battle.py` 第 `[21]` 节，**清单是查库得出的，
  不是抄在代码里的**——库里多一个就该失败）：

  | 技能 | 键名 | 语义 | 处理 |
  |---|---|---|---|
  | 阿米娅(近卫)技1 影霄·奔夜 | `prob` | **60% 法术闪避** | 期望值法已覆盖 |
  | 赤刃明霄陈技2 赤霄·绝影-驰 | `chen3_s2[respawn_buff].prob` | **60% 物理和法术闪避** | 期望值法已覆盖 |
  | 提丰技2 冰原秩序 | `attack@prob` | **40% 概率晕眩 1 秒** | **不能沿用**，见下 |

  **`prob` 这个键名同名反义**——赤刃的 `prob` 是闪避率，提丰的 `attack@prob`
  是控场概率。按键名认必错，只能按**描述**判。
- [x] **随机·提丰技2 的概率晕眩**（2026-09-18 落地，守卫 `check_battle` 第 [22] 节）：期望值法**不是对所有随机都成立**。
  它对闪避成立，是因为"一次攻击被闪掉的概率"可以**线性折进伤害**；而晕眩是
  **离散的控场状态**，不是伤害系数——把 40% 折进伤害会算出一个既不是伤害
  也不是控场的数。

  落地要做两件事，本轮只查清了范围、没有实现：
  1. **敌人侧加晕眩状态**。现在 `stun_timer` **只在干员侧有**，敌人侧一个都没有
     ——所以"提丰技2 未建模"是事实而非推测。晕眩对敌人 = **不能动 + 缴械**，
     现有 `disarm_timer` 只管了后一半，移动那一半也要接上。
  2. **按期望占比而非掷骰**：每次命中给敌人的晕眩计时**加上**
     `attack@prob × attack@stun`（0.4 × 1.0 = 0.4 秒），计时器照常递减。
     这样当攻击间隔 > 0.4s 时，稳定占比恰好是 `0.4 / 间隔`（正确）；间隔
     更短时计时器持续为正 → 敌人一直晕（**这正是该有的封顶**，不会越界）。
     注意是**加**不是 `max`：用 `max` 会在间隔小于 0.4 秒时把占比**低估**成
     单次时长。

  审计里那条**跳线已于 2026-09-18 踩响并改口**（第 [21] 节现在钉的是「已有晕眩
  状态」）。落地是：`EnemyUnit.stun_timer` + 移动闸门（`advance`）+ 两处攻击闸门；
  施加点挂在 `_damage_enemy` 的 `_enemy_on_hit`——它已经是「打敌人的**单一出口**」，
  而且**已经带 `source`**，不用再散挂。

  **踩到两个坑**：

  1. 黑板挂在 **`SkillLevel`** 上，**不在 `SkillEffects`** 上。第一版写的是
     `getattr(eff, "blackboard", None) or {}`，它会**静默拿到空字典、永远不上晕**
     ——而"没上晕"与"这个技能本来就无晕"在输出上一模一样，只有守卫能发现。
     已改成直接取属性，取错就抛。
  2. 按「描述里有『晕眩』」挑技能会挑到**技3「永恒狩猎」**——它的描述里也有
     「晕眩」，而且用**另一套键**（`attack@s3_stun` / `attack@s3_trigger_time` /
     `attack@s3_max_hit_num`），触发条件是"每 8 秒内的前 4 次攻击"，与技2 的
     "每次攻击 40% 概率"不是一回事。必须**按名字**挑技能。

  **技3 那套晕眩未建模**（本实现只认 `attack@prob`/`attack@stun`），第 [22] 节里
  有一条守卫如实钉着它，免得"提丰的晕眩做完了"被当成两套都做完了。

  期望占比的落点：每次命中给计时**加** `0.4 × 1.0 = 0.4` 秒。守卫观测到的最大值是
  `0.3667 = 0.4 − 1/30`——观测点在 `advance`，同帧的递减已经先跑过了，差的正好是
  一帧。判据因此写成 `[0.4 − 1帧, 0.4]`，**上限那一半才是关键**（间隔 > 0.4s 时
  不该累积）。
