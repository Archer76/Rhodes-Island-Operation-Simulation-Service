# 关卡环境机制（战斗层）

`ak_tactic/battle/environment.py` + `tools/check_environment.py`。
文本层（把机制正文编译成公式项）见 `mechanics.md`，两者是**两层**：
那一层回答「这一关用了哪些机制、正文被形式化成了什么」，
这一层回答「机制跑起来是每秒掉多少血」。

第一个落地的消费者是**怀黍离的田地 / 病害值**。

## 一、三条事实来源，各自可分辨

| 来源 | 给出什么 | 取法 |
|---|---|---|
| 关卡 JSON `runes[key=env_system_new][].blackboard` | **五个数值参数** + 初始污染点 | `PolluteParams.from_stage` |
| prts.wiki「特殊机制」页 + 关卡页字段 | **公式的形状** | `mechanics.parse_mechanic` |
| 关卡 JSON `mapData` | **哪些格是田地** | `is_farmland` / `farmland_cells` |

两条来源互为校验：HS-8 页写「20+病害值×3 / 100+病害值×9」，
而黑板里正是 `basic_damage=20 / damage_ratio=3 / first_basic_damage=100 /
first_damage_ratio=9`。自检里有一条逐项对照钉住这个吻合。

## 二、黑板怎么读（踩过的真错）

黑板条目形如 `{"key":…, "value":<num>, "valueStr":<str|null>}`：

* **数值型键的值住 `value`**，`valueStr` 恒为 `null`；
* 只有 `init_pollut_value` 这类字符串住 `valueStr`。

只读 `valueStr` 会得出「五个参数全是 None」，并进而误判
「环境系统不在 gamedata 里」——**这个假结论在本项目真出现过**。
自检里因此有一条专门断言「数值键的 `valueStr` 是 None」。

## 三、⚠ 难度掩码：禁止取第一条，且 **`ALL` 必须认**

同一个 `env_system_new` 在关卡里常有多条，靠 `difficultyMask` 区分，
实测取值有三种：`NORMAL` / `FOUR_STAR` / **`ALL`**。

* 取第一条会静默画错污染点（`act31side_ex08`：NORMAL `1,1:0` vs
  FOUR_STAR `4,4:100`）；
* 只认 `NORMAL` 会**整条漏掉** `act31side_08`（它用的就是 `ALL`），
  而且不报错——环境伤害静默变成 0。

匹配规则：`mask == "ALL" or mask == 难度`。

## 四、坐标：`init_pollut_value` 的 row 要翻一次

格式 `"row,col:value"`，其 row 是**游戏内部口径（自下而上）**，
解析时翻一次 `y = 高 - 1 - row`（与 `routes[].row` 同规矩，见
记忆里的「地图不翻、路线翻」）。

自证：`act31side_08` 写 `7,1:100`，图高 9 → `y=1`；而该关情报写
「场地**左上角**田地区的初始病害值+100」，翻过来正是靠近顶部那一行。
不翻则落到 `y=7`，与情报相反。

## 五、田地判据（第三版，待实机校正）

```
田地 = heightType == "LOWLAND"  且  tileKey ∉ {tile_telin, tile_telout, tile_hole}
```

依据是 prts.wiki「田地」原文「仅适用于**地形标记**为**默认**的地面地块
（传送门出入口/地穴除外）」。

⚠ **必须按 `tileKey` 的名字判，不能只看字段。**
`tile_hole` / `tile_telin` / `tile_telout` 的
`(heightType, buildableType, passableMask)` 与普通低地**完全一致**，
字段分不出来。这不是理论顾虑：`act31side_08` 真有一条 5 格长的地穴竖墙，
只看字段会把它当成可通的田地，把本该分开的两片连成一片——
自检里有一条就断「地穴墙把田地切成 2 片」。

⚠ 反过来，`tile_start` / `tile_end` / `tile_fence_bound` / `tile_flystart`
**仍然是田地**。第一版自造过一个把它们也排掉的排除集，被博士的地图预览图证伪。

## 六、模型：谁共享什么

原文两句话是**分开**写的，所以粒度也不同：

* 「田地拥有【实际病害值】」 → **按格**（`actual: dict[cell, float]`）
* 「未被隔断的连片田地拥有共同的【最大病害值】」 → **按连通域**（`Field`）

这个区分不是抠字眼，是阻流阀那条规则逼出来的：「被隔断的组各自取当前
最高【实际病害值】作为新的【最大】」——若 `实际` 也按组存，
「各组当前最高」就无从谈起。

连通域用**四邻**：斜向相接的两格在游戏里不共享病害。

【缓存】是加在**【最大】**上的（原文「每 0.2s 释放 1 点**累加至当前的
【最大病害值】上**」），装置（泵站、天桩）走 `add_cache`。

## 七、⚠ 三处歧义（都留在代码里，没有偷偷选）

1. **靠拢步长有两种读法。** 原文「与最大值的差值每25点+1实际病害值，
   小数部分上入」：
   * **甲**（`base=1`，博士 2026-09-17 记录的口径，**当前实现**）：`ceil(差值/25 + 1)`
   * **乙**（`base=0`，原文直读）：`ceil(差值/25)`

   两者相差恰好 **1 点/秒**。改 `ACTUAL_BASE_STEP` 即可切换，两种读法都有自检盯着。

2. **初始播种的粒度。** 数据是「坐标 + 值」（`7,1:100`），当前实现把那一格的
   【实际】设为该值、把所属田地的【最大】抬到该值，**同组其余格子仍从 0 爬升**。
   另一种读法是整片播种（同组每格都从该值起）。开场那一秒差 320 点伤害。
   取逐格的理由是 `act31side_ex03` 给了**两个**点（`5,5:90|5,3:90`）而它们落在
   **同一片**田地里——整片播种会让第二个点冗余。**这个理由不是定论。**

3. **爬升是渐近的，不是恒速。** 步长 `ceil(差值/25+1)` 随差值缩小而变小，
   差值 100 时每秒 +5、差值 25 时 +2。实关实测：**30 秒才到 97，到不了 100**。
   （我第一版按恒速 5/秒 写过断言「20 秒后到 100」，跑出 77 才暴露——
   所以自检的判据是**逐秒对拍那条规律**，而不是某个秒数上的某个数。）

## 八、结算

```
病害值 = 0   →  每秒回复 hp_recovery_per_sec（恒 50）点生命
病害值 > 0   →  每秒受到 basic_damage + 实际病害值 × damage_ratio 的环境法术伤害
部署瞬间      →  额外受到 first_basic_damage + 实际病害值 × first_damage_ratio
```

原文两句分开写，所以**部署瞬间那一下是额外的，不是每秒结算的第一次**。

不作用于高地——这不需另判，田地判据本身就要求低地。

## 九、接进模拟器

`BattleSimulator(..., environment="auto" | "off", environment_difficulty=...)`。

* `auto`（默认）——这一关的 `runes` 里有环境系统就自动开启。
  **没有则一个对象都不建**，绝大多数关卡走这条，零开销。
* `off` —— 显式关掉，用于回归对照。

接线三处：构造时建 `FarmlandSystem`；`_do_deploy` 里结算部署瞬间那一下；
主循环 3.7 步 `_environment_tick` 里推进病害值并按整秒结算。

**伤害按整秒结算用整数计数而非 `>= 1.0` 后清零**：掉帧时 `dt` 可能跨过
不止一秒，只结一次等于把伤害漏掉。`fps=30` 时不会发生，但 `fps=1` 的粗扫会——
而粗扫正是搜索里用得最多的档。

### 接线的效果有多大（实关实测）

`act31side_08` 的有病害那片田地里**有 10 个可部署格**（`(10,3)` 一带）。
但它们在开场时【实际】为 0，按渐近规律爬升：1/10/20/30 秒 = 5/45/77/97 点，
对应每秒伤害 35/155/251/311。所以**站进去是先安全、后越来越疼**，
而不是一落地就吃满伤害——这个形状完全由第七条那处播种歧义决定。

## 十、关卡装置

装置与干员不同：**它们由关卡摆好**，数据在 `predefines.tokenInsts`。
入口是 `ak_tactic/battle/devices.py`。

⚠ **三个坑**：

1. **`prefabKey` 这个字段不存在。** 装置身份在 `inst.characterKey`
   （`prefabKey` 只在敌人/召唤物那边用）。照着它取会得到一列 `?`。
2. **`position.row` 自下而上**，与 `routes[].row` 同规矩，翻一次 `y = 高-1-row`。
   实关判据：`act31side_08` 的 26 个装置**全部落在田地上**（26/26）；
   不翻的话它们会整批落到图的另一侧、落到高台或图外。
3. **`direction` 是屏幕方向**，与内部 y 轴朝哪边无关，故 `UP` = MAA 的 `y-1`。

act31side 全 24 关只用了三个装置：

| characterKey | 名字 | 出现在 | 效果 |
|---|---|---|---|
| `trap_139_dhtl` | 阻流阀 | 23 关 ×128 | 「3秒后建成，阻隔水流」→ 自身地块不再是田地 |
| `trap_146_dhdcr` | 天桩 | 10 关 ×36 | 「登场时，在自身所在位置以预设路径召唤一名天桩-甲」 |
| `trap_140_dhsb` | 泵站 | 8 关 ×14 | 「将身后一格的浅水泵至前方…」 |

**天桩仍不实现效果。** 它的技能「生成」在库内**正文为空**（黑板只有 `branch_id`），
可正文并非取不到——prts.wiki 的「天桩(装置)」页写得很清楚：

> （被动）登场时，在自身所在位置以预设路径召唤一名天桩-甲（或失控天桩-甲）
> 于所在地块的天桩-甲（或失控天桩-甲）退场时死亡 ｜ 阵营 敌方 ｜ 生命值 100 ｜
> 不可撤回 ｜ 不可被玩家查看

也就是说天桩是**生成器 + 绑定性命**：它自己不战斗，命挂在它召唤出来的那个
**敌人**身上。要做到它，得先能实现「天桩-甲」这个敌人（监测形态无敌不死、
生命百分比与所在地块病害值同步、≥100 激活；激活形态每秒自伤 1% 最大生命、
每损失 10% 生命延迟召唤 3 个天桩-乙），**那是一条比装置层长得多的链**。
按本项目惯例**不为它编效果**：编不出来是漏，编错了是错。
正文已抄进 `ak_tactic/activity.py` 的登记表（`trap_146_dhdcr`，状态 TODO），
那里是它唯一的落点。

### 阻流阀建成会**改变田地几何本身**

这是本机制最容易漏的一环：阻流阀不是"加个状态"，而是把自身地块从田地里
摘掉，**连片的田地因此被切断，【最大病害值】的共享范围随之重划**。
`act31side_08` 里它建成后田地由 **2 片变 7 片**。

建成耗时取自装置自己的技能 `duration`（「阻流3秒后建成」），
`devices.BUILD_SECONDS = 3.0`，由 `sim._environment_tick` 在到点时一次性结算。

⚠ 该关 16 个阻流阀**并非全在同一行**：y=1 有 10 个（x2–11，是一道坝），
其余 6 个散在 y=3/4/5/6/7。我先前只看探针打印的前 12 个装置，
就断言「16 个排成一列」，被自检拦下——**探针的截断输出不能当全集用**。

## 十一、水位与判据

命令：

```
python tools/check_environment.py
```

**不在这里写水位**——它每加一段机制就变一次，写死只会变成过期的诱惑。
以自检输出为准。判据（**不是水位**，低于即说明被改坏）：`ALL` 掩码必须生效；
地穴墙必须把田地切成 2 片；装置必须全部落在田地上（行翻转的实关判据）；
阻流阀建成后田地片数必须变多；靠拢步长的两种读法都必须能算；
第三节的敌人侧机制必须逐条为真。

### 泵站（`trap_140_dhsb`）

效果**全在正文里**，黑板是空的。权威原文（prts.wiki「泵站」装置机制）：

> 部署后若自身身后一格为田地，且自身前方生效范围（默认身前一格）存在可用的
> 田地时执行泵水：将身后一格的水泵至生效范围
> · 若水源地为清澈（病害值=0），则以每秒 1 点的速度**降低**目标格所在连片田地【最大病害值】；
> · 若水源地为污染状态（病害值>0），则以每秒 1 点的速度**增加**目标格所在连片田地各田地
>   【当前病害值】及【最大病害值】，当 目标格所在连片田地 ≥ 水源地 的【最大病害值】时停止增加；
> · 若水源地部署有我方单位，自身生效范围 +2；
> · 同一泵站对同一连片田地只生效一次增减效果，多个泵站作用于同一连片田地时效果可叠加

三处容易被"顺手续上"的地方，代码里都按原文边界停住：

* **两个分支不对称**：清澈那一支**只降【最大】**、不动各格【当前】；
  受污那一支**既抬【最大】也抬每一格的【当前】**。这是原文自己写的，不是笔误。
* 受污的停止条件是 **目标组【最大】≥ 水源地【最大】**（组间比较），
  **不是**"等于水源地那一格的病害值"。
* 「生效范围 +2」加的是**前方格数**（1 → 3），**不是**攻击范围那种几何。

⚠ 实关里泵站的水源地**多半是清澈的**（8 关 14 个泵站，开场【实际】>0 的几乎没有），
所以**受污那一支必须用构造场景测**——只跑实关会把两个分支漏掉一个，
而覆盖率看着还是满的。

## 十二、敌人侧的关卡机制

前面各节是**地图**（田地、泵站、阻流阀），这一节是**敌人身上**的机制——
它们由关卡的 `enemyDbRefs` / `talentBlackboard` 给出，入口是
`ak_tactic/gamedata/enemy.py` 的 `mech_fields()`，运行时结算在
`battle/sim.py` 的 `_enemy_on_hit` / `_enemy_mech_tick` / `_pm2_tick` /
`_reborn_tick` / `_on_enemy_death`。

### 敌人黑板怎么读

* **数值在 `value`、文本在 `valueStr`，且 `valueStr` 非空时 `value` 是个 0 占位。**
  合并两个来源时若先看 `value` 再看 `valueStr`，字符串键会被**整体丢掉**；
  正确规则是「`valueStr` 非空则用它，否则用 `value`」。全库核对过：
  531 条字符串条目里，`valueStr` 非空而 `value` 非零的有 **0** 条，所以这条安全。
* **两类前缀各成一套机制**：`Reborn.`（死志的凝结）与 `Reborning.`（瘴 / 鄙瘴 / 祟）
  是**两套不同的键**，不是拼写差异。⚠ 我先前硬编码 `"Reborn.reborn_duration"`
  去判"要不要重生"，结果 `Reborning.duration` 的两族敌人**静默地不重生**——
  没有任何报错，只是场上少了几条命。现在由 `_REBORN_SPECS` 表判。
* **同一前缀下有两条互不相干的分支**：`Reborning.` 既能是**充能**（瘴 / 鄙瘴：
  有 `value` 与 `def_add` / `damage_magic`），也能是**召唤**（祟：有 `enemy_key` /
  `cnt`，没有 `value`）。按"有 interval 就是充能"去读，会把祟算成
  「每次扣 0 点病害值」的充能怪，**而召唤整支消失**。判据是 `enemy_key` 在不在。

### 六类机制与它们的判据

| 前缀 | 机制 | 关键量与边界 |
|---|---|---|
| `Passive.` | 被击倒时污染田地 | `extra_value`（秽/除秽 5、肮/厌肮 15）、`range_radius` 1.0 |
| `DeathPassive.` | 被击倒时给予可部署装置 | `token_key` / `cnt`（**只记账，见上**） |
| `AuraHit.` | 进入阻流阀范围立刻真伤 | `hp_ratio` 0.5 / 0.7，半径 0.5（**未实现**） |
| `SpeedUp.` | 受击且未被阻挡时加速 | `move_speed` / `duration` / `cooldown` |
| `Passive_Hit.` | 「祟」受击蜕皮 | 每 `cnt`(=4) **次**伤害叠一层，`max_stack_cnt`(=80) 封顶 |
| `PassiveM2.` | 「祟」明识形态 | 属性改写 + 标记 + 清水分支 |

### ⚠ 四处的读数与边界（不许"顺手取整"）

1. **污染圆心随"有没有被阻挡"换位置。** 原文是
   「令阻挡自身的单位(被阻挡时)/自身(未被阻挡时)半径 1.0 范围内的田地地块…」——
   **括号是条件，不是补充说明**。两种情形落在不同格子上，自检里两条都测了。
2. **半径 1.0 是圆，不是方。** 1.0 恰好够到上下左右四邻（距离 1.0）、够不到斜角
   （√2 ≈ 1.414），共十字五格。对比：天桩-甲那一侧写的「1.0 边长正方形」是**方**，
   两者不能混用同一个辅助函数。`environment.cells_in_radius` 是圆那一套。
3. **加速要写进 `haste_multiplier`，不能并进 `speed_multiplier`。**
   后者被积雪天赋**每帧重写**，并进去会被当场抹掉且不报错。同样写
   `haste_multiplier` 的还有明识形态的移速加成，所以两者**不能挂在同一个敌人身上**
   （自检里有一条假设守卫盯着这件事）。
4. **明识形态的清水分支是"两个百分比同桶相加"**：`defense = 基准 × (1 - 0.7 - 0.15)`，
   不是 `× 0.3 × 0.85`。库里的两套键是**同一个属性桶**里的两个负向修正，
   与本项目干员侧的口径一致。

### runes 的敌人修饰层

`ak_tactic/battle/stage_mul.py`。三个键（+两个老名字）：

| 键 | 作用 | 老名字 |
|---|---|---|
| `enemy_attribute_mul` | 缩放 atk / def / max_hp，可带 `enemy` 点名 | `ebuff_attribute` |
| `enemy_talent_blackb_mul` | 乘敌**天赋**黑板（`Passive.extra_value` 等） | — |
| `enemy_skill_blackb_mul` | 乘敌**技能**黑板（按 `skill` 的 prefabKey 点名） | — |
| `global_lifepoint` | 覆写**生命点** | `gbuff_lifepoint` |
| `cbuff_cost_recovery` | 费用回复**速度**倍率（实现里是**除**） | — |

⚠ **老名字必须认**：`main_01-07` 的四星档用的就是 `gbuff_lifepoint` /
`ebuff_attribute` / `cbuff_cost_recovery`，只认新名字会让老关卡的难度档**整体失效**
而毫无提示。别名表在 `stage_mul._ALIASES`。

⚠ **同键多条是"依次相乘"，不是"覆盖"。** `act31side_ex02` 四星档同时有
「全部敌人 ×1.2」与「点名 ×1.5」两条，那个被点名的敌人是 **×1.8**。
解析函数返回的是**列表**而不是字典，就是为了不让后一条把前一条吃掉。

⚠ **乘完必须重算派生字段。** 乘数落在 `talent_blackboard` 那张表上，
而运行时读的是 `MechanicFields` 派生出来的 `passive_pollut` 之类的字段；
只乘黑板不重算，机制**一点都不会变**（`derive_blackboard_fields` 就是干这个的）。

⚠ **改副本，不改库。** `EnemyLibrary` 是跨关卡共享的对象，就地改会让"下一关"
莫名其妙变强。`apply_rune_muls` 命中时先 `clone()`，自检里有一条专门核对
"乘完库里还是原值"。

### 覆盖盲区（这一段是这一节存在的理由）

**怀黍离不在三条回归基线里**（1-7 / SR-6 / SR-EX-8 都没有这套机制），
所以这些机制**拿不到"真关卡跑出来的数"来对**。为了不让"看起来跑通了"冒充
"确实跑对了"，验证分两层：

* **构造场景**（`tools/check_environment.py` 第 10 节）：用桩敌人 + 桩干员逐条对，
  并**明说哪条分支在真实关卡数据里不可达**；
* **真几何上的整条链**：`act31side_ex08` 有「祟」，按关卡自己的出怪路线把它摆出来，
  打掉它、走完 倒下 → 8 秒/20 秒两路召唤 → 40 秒归来 → 明识形态，
  用的就是这张真地图的寻路、装置与田地。

冒烟（`_proto/hsl_e2e.py`，整条时间线跑完看机制有没有真的响）：

```
python _proto/hsl_e2e.py act31side_08      # 死亡污染 / 加速 / 重生充能 / 给装置
python _proto/hsl_e2e.py act31side_ex08    # 死亡污染 / 蜕皮
```

⚠ 这两关**都是构造场景**（冒烟里临时放大了生命点好让时间线跑满），
**不是成绩单**，别把它们当基线。真基线只有三条：1-7、SR-6、SR-EX-8。
