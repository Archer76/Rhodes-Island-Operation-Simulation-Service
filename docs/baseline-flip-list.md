## 第二轮取证（引擎身份探针）：**标签是真的，漂移在 Go 自己身上**

UI_2b 发现：台账「旧读法 vs 原版 Python」那一栏的 `83杀/1漏/814.0333s/591046.1`，与 19:08 那枚老
Go 二进制测出的**逐位相同** ⇒ 怀疑"Python"这个**标签**贴错了（本树有过同型事故：引擎切 Go 之后
裸 `Verifier()` 其实跑 Go 却照打 `[python]`）。**怀疑的是标签而不是数字，这比数错更难查。**

新工具 `tools/engine_identity_probe.py` 给三样硬证据：**声明的引擎名 / 实际加载的模块文件路径 /
消费者计数器**（Go 客户端被调用几次、原版 Python 入口被调用几次——**计数为 0 的那一侧就是没跑**，
与它叫什么名字无关）。另报 `go_runs` / `go_fallbacks`：`simgo/verifier.py:95` 有一条**静默退回**
（规格里有 `unsupported` 字段时，走 Go 的那条路**直接跑原版 Python**）——只报 `go_fallbacks` 不够，
**计数器才是主证**。

实测（`fixtures/hsex8_max.json`，同一名册、同一 `spec_sha=464a9dc2…`）：

| 跑法 | 判决 | 计数器 | fallbacks | 结论 |
| --- | --- | --- | --- | --- |
| A · 钉 `engine="python"` | 83杀/1漏/**814.0333**s/591046.1 | Go **0** / Py **1** | — | **真的是原版 Python** |
| B · `engine="go"` + 19:08 老二进制 `b3e4d6b1` | 83杀/1漏/**814.0333**s/591046.1 | Go **1** / Py 0 | **0** | **真的是 Go**（无退回） |
| C · `engine="go"` + 当轮自建自钉 `9b81f2d5` | 48杀/3漏/**221.6667**s/282276.8 | Go **1** / Py 0 | **0** | **真的是 Go** |

⇒ **PM 给的三条判据里，②与③都不成立，因为它俩的前提（"两个引擎的数不同"）在这一对上不成立**：
标签**是真的**（A 确实跑的是原版），数字**也真的相同**——**相同的原因是 19:08 那枚 Go 二进制与
Python 一致，而当轮的 Go 二进制不一致**。

**这条的性质变了**：这不是"Python 与 Go 的分歧"，而是 **Go 自己在两次构建之间漂移了**
（19:08 那枚 ⇒ 与权威实现 Python 逐位一致；23:0x 之后的那枚 ⇒ 48杀/221s 落败）。
⚠ **而我们的 Go 基线记于 22:13 那枚**（`b88b28ce6d0ca14f`）⇒ **换基线的时候，把这段漂移一起固化了**：
基线里那句"与 Go 基线一致"，量的是**已经漂移过**的 Go。

**两个方向都还开着，不许挑一个当结论**：
* **Go 修好了**：19:08 那枚还没移植某条会让 HS-EX-8 变难的机制（近期提交里有若干机制移植，
  例如「冻结闸门接进敌方技能出手：第 4 手 18杀 → 19杀」），Python 反而是过宽的那一侧；
* **Go 退化了**：某笔提交把"打不过"写进了 Go，Python 才是对的（Python 在裁定前是**权威实现**）。
⇒ **定性动作＝在这两个构建点之间做二分**（逐提交构建 exe，看 814.0333 在哪一笔翻转），归 PM/后端；
本报告只把**事实与仪器**钉住。

## 第三轮取证：`source_sig` 的两个数——**根因是同一名字写了两份公式**

后端2 复现不出我报的 `2a9c381a`（它两棵树都算 `9b81f2d5`）。**同一时刻对算（2026-09-19 23:56:29，
`rios-sim` **0 条脏**、glob `rios-sim/**/*.go`、29 个文件）**：

| 算法 | 值 |
| --- | --- |
| ① 验收门**原先自己那一套**：`名字:大小:mtime` 摘要 | **`2a9c381a`** |
| ② `tools/engine_pin.py` 的**内容**摘要（disk） | **`9b81f2d5`** |
| ③ 同一份内容的 **HEAD** 版 | **`9b81f2d5`** |

⇒ **根因不是"算的时刻不同"，是同一个名字底下有**两份不同的公式**（一份摘 mtime、一份摘内容）
——正是后端2 前一条刚提醒过的"两处各写一份，一改就对不上"，而**制造它的是我**。
处置：`acceptance.py` **删掉自己那份**，统一 `from engine_pin import source_identity`；
门第 0 项现在打印 **disk / HEAD / dirty 条数与名单**。

`engine_pin` 顺带定下两个身份（PM 2026-09-19 23:55 裁定）：
* `source_sig`（disk）＝**磁盘此刻**；取它**必须同时报 `source_dirty` 条数与脏文件名单**；
* `source_sig_head()`＝**从 HEAD 的 blob 算**（检出无关：HEAD 里没有的文件**跳过**，不记空串）；
* **判「这台仪器是不是 HEAD 的构建」只能用 head 版**；只用 disk 版时**必须明说**。
* **反向守卫**（`python tools/engine_pin.py --selftest`）：写一枚**不提交**的 `.go` ⇒
  disk **必须变**（实测 `9b81f2d5` → `b8af58eb`）、head **必须不变**（实测不变），删掉后两者都回原值。

## 机制：为什么"换了参照物"比"修好了"危险

被判据判红的条目会**逼人去看它**；而被换尺子变绿的条目**安静地消失**。
所以本清单的规矩是：**换基线的同一个提交里，就要写下"哪些条目因为这次换尺子而不红了"**，
并逐条给出**它被修复的证据**或**"未归因"这四个字**——**没有第三种写法**。
