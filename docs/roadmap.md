## 〇 · 先读这三条

1. **不做近似**（博士裁定）。目标是完整建模所有机制；未完成的机制用**具名占位**
   标记，解算遇到即拒判（Incomplete），不给肯定判决。本文的「缺失」都以这套占位为准。
2. **Python 不是标准**。Go 引擎按独立实现对待；与 Python 的差异不自动算欠账，
   冻结档只当变化探测器。
3. **本文是清单，不是证明**。每项的「现状」来自源码与已归档报告；
   动工前必须对当前源码重核一遍——行号与数字会漂。
4. **三条轴分开报告**：实现完整性、运行期行使、正确性证据不能互相替代。
   数据可读取、规格可装配、没有占位、与 Python 一致，均不能单独证明完整模拟。
   零占位只表示生产检测器未检测到缺口；纯描述、脚本及未进入检测器的行为仍可能漏标。

## 一 · 状态图例与更新规则

| 标记 | 含义 |
|---|---|
| ⬜ | 未开始 |
| 🔶 | 部分完成（写明已覆盖与未覆盖的边界） |
| ⏸ | 等裁定或外部证据（写明在等什么） |
| ✅ | 已完成（写提交号；完成后移到第九节） |

更新纪律：

- 一项完成时写**提交号＋实际运行的测试计数**（PASS／FAIL／SKIP，SKIP 不算过）。
- 只完成一部分时，把未覆盖部分**拆成新行**，不要把整项标 ✅。
- 新发现的缺口直接加行，标出处（文件、报告或会话日期）。

### 9.5 由普查决定的后续顺序

1. **修完整性检测的漏口**：非攻速模组、敌方技能、P3R 和关卡控制器／词条来源；先拒绝错误肯定。
2. **高频且能分族验收的消费者**：技能范围（174 角色／220 无模组组合），事件／计数／条件来源。
   `cnt`、`interval`、`atk_scale` 同名不同义，绝不能按键一刀切。
3. **实体与状态系统**：召唤、位移、变体／形态，覆盖干员与敌方的生命周期联动。
4. **关卡目标与缓存补齐**：划清普通战斗、特殊模式和非战斗范围，再补未知内容；保留排除六星裁定。
5. **行使与正确性验收**：对已经认领的来源补正负战斗夹具、解锁边界与独立机制证据。

结论：已有通用数据与战斗底座，但检测器对绝大多数所测干员配置仍会给出占位，
敌人／关卡侧还存在大规模未识别来源和未缓存数据。**不能宣称接近全覆盖，也不能把 4.14% 当完整模拟率**。
未来重复同口径普查时，必须固定源码与数据版本，分别观察缺口、未知和零占位变化；
只有再加上行使与正确性证据，才能谈完整模拟进度。
